# API v1 route table

Base path `/api/v1`. JSON in and out. Bearer token auth on everything except `healthz`, the OpenAPI document, `login`, `login/github` and `auth/github`. A sign-in token (scope `signin`, see `requirements/login.md` 2.2b) opens only `login/orgs`. Errors are RFC 9457 problem+json (`apitypes.Problem`) with a `hint` an agent can act on. A token stops working the moment its user is suspended (403 "user is suspended") or deleted (401 "user is deleted"), whatever its expiry. Password and GitHub sign-in refuse such a user with the same status and hint. An agent acts only within its owner's current rights: it stops when its owner is suspended (403 "agent's owner is suspended"), deleted (401) or removed from the org (403), its org role is capped at its owner's, and in each project it holds the lower of its own role and its owner's, so a project its owner cannot see is 404 to it. Wire types: `internal/apitypes`. The OpenAPI 3.1 document is served at `/api/v1/openapi.json`.

## Ids, numbers and cursors

- Every entity has a snowflake id, sent as a decimal string. Cards (tasks, questions, stories and decisions alike) have a per-project number (`#42`). URLs use numbers for cards, a slug or an id for notes, and ids for agents, tokens and events.
- Actors are `{kind: user|agent, id}`. No names travel with cards, events or claims: clients resolve ids with `GET /actors?id=1,2,3` and cache the result.
- Lists page by keyset. Every list response carries `next`, `prev` (opaque cursors, pass one back as `?cursor=`) and `remaining` (rows beyond the page in that direction, capped at 100). A cursor from another list, or a malformed one, is a 400. Full-text lists (`q=`) are ranked and go forward only: `next` and `remaining`, no `prev`, and `next` only while more follow. A cursor from a list with `q` is a 400 on one without it, and the other way round. A card cursor also names the sort and direction it was issued for; using it with a different `sort` or `desc` is a 400, the same as any foreign cursor.
- `/projects`, `/projects/{slug}/members`, `/members`, `/agents`, `/tokens`, `/locks` and `/claims` only go forward: `limit` defaults to 50 and stops at 200, there is no `prev`, and `next` is present only while more follow.
- List filters take RFC 3339 instants (`2026-10-20T00:00:00Z`); the server does no relative or calendar-day parsing, clients resolve those. `*_after` is inclusive and `*_before` exclusive, so a window is `[after, before)`; `after` not earlier than `before` is a 422. An unparsable instant, actor or enum value is a 422 naming the field.
- Events page by position: every event carries `position`, and `after=<position>` returns newer events, `before=<position>` older ones. Omitting both starts at the oldest event; `before=9223372036854775807` (the largest id) returns the newest page. Feed order is commit order, not id order: an event appears once every transaction that started before it has finished, and a later page can hold an event with a lower id than the one before it. Positions compare as strings in feed order (`internal/server/cursor.go` `eventPosition`); ids do not, so never compare ids to decide what is newer. Every event cursor also takes a bare event id, which clients saved before positions existed. A cursor that names no event of the org (an unknown id, or a position whose xid is not that event's, as after a move to another database) is a 422 on that field (except the largest-id sentinel above); start again without it. `next` and `prev` of an event list, the inbox `cursor` and the stream's resume point are positions.

## Headers

- `X-Lorvik-Cursor` (request): the caller's inbox cursor, an event position (`0` for the beginning). When sent, the response carries `X-Lorvik-Unread`: events by others since that cursor, counted up to 101 (`apitypes.UnreadCap` plus one), so 101 means "more than 100".
- `X-Lorvik-Session` (request): a label for the calling chat or process, 1 to 40 characters of lowercase letters, digits and hyphens (`apitypes.ValidSession`); anything else is 422. `claim` records it on the claim it creates (empty when the header is absent); `renew` and the automatic renewals keep the original claim's session. Cards expose it as `claim.session`. For an agent the claim belongs to that session: claim, start and transitions from another session of the same agent are 409 while the lease is live, renew and release 403, and automatic renewals touch only the calling session's claims. `GET /events/stream` renews no claim. A human's claim is the human's in any session.
- `Idempotency-Key` (request): on `POST /projects/{slug}/cards`, `POST /projects/{slug}/cards/{number}/comments` and `POST /projects/{slug}/cards/{number}/transition` only; every other route ignores it, and without it nothing changes. 1 to 64 characters of letters, digits, hyphen and underscore (`domain.ValidRequestKey`); anything else is 422 naming the header. The same key from the same caller makes the write happen once: a repeat returns what the first request made, with the route's normal success status (the card created, the comment stored, the card as it is now for a transition), and writes nothing and emits no event. It is answered before the body, the card's version or status or the caller's right to write is checked, so a resent `done` whose first attempt was applied gets 200 with the card, not 409. A key first used for another operation, project or card is 422 naming the header. Keys are per caller: another user, or another agent, sending the same string is not a repeat. Keys do not expire, since a write can wait in a client's queue for any length of time. The CLI sends it on `comment`, `add` and `done` it queues while the server is unreachable.
- `X-Lorvik-Session-Name` (request, agents): what people call the calling chat, percent-encoded UTF-8. The server cleans it (control characters and invalid UTF-8 become a space, zero-width characters and direction overrides are dropped, runs of white space one space, at most 60 characters), keeps the last one sent for the chat's base label and returns it as `session_name` beside `session` on `Claim`, the live claims and `Lock`, as `name` on an agent's `sessions`, and as `session_name` on the agent's own `Me`. A value that does not decode, or is empty once cleaned, names nothing. A request without the header leaves the stored name alone.
- `X-Lorvik-Token` (response): a successor secret. A token used inside its last 7 days (`domain.TokenRotationWindow`) is replaced; the old secret keeps working for 24 hours (`TokenRotationGrace`), then any use of it is recorded as `token.reuse_detected` and answered 401. Tokens whose whole life is under 14 days never rotate. Clients store the new secret the moment they see the header.
- `X-Lorvik-Holding`: a request that carries it (any value) is answered with the same header holding what the calling chat holds once the request has done its work, so a claim names its card and a release does not: base64 of the JSON `Holding` `{cards: [{project, number, title, expires_at}], more}`. The cards are a person's live claims, or an agent's in the calling session, the soonest to end first; at most 8 are named, fewer when the value would pass 2 KiB, with titles cut to 60 characters, and `more` counts the rest. `GET /events/stream` does not answer it; a listener's requests do, and being told renews nothing.
- Every authenticated request renews the caller's claims that are past half their lease, except `GET /events/stream` and any request that carries `X-Lorvik-Listener` (any value): a background listener sends it on everything it does, because a listener running is not the chat working.

## Roles

Five roles, in order: viewer (10), member (20), reviewer (30), admin (40), owner (50). A role is held org-wide (membership) or per project (project member); the effective role in a project is the higher of the two. Private projects need a project role; admins and owners see everything. An agent's rows hold viewer, and its rights (below) say what else it may do. Who may do what for a person is `domain.minRole`:

| Permission | Minimum role |
|---|---|
| read | viewer |
| card write (own cards), question ask, decision propose, note write, comment write | member |
| card triage (edit or drop any card, take over claims), card ready (move anyone's backlog card to ready), question answer, decision accept/reject/revoke | reviewer |
| agent manage, project manage, member manage | admin |
| org manage | owner |

Read-scope tokens cannot do anything in the member row or above.

### Agent rights

An agent reads where it has an alive row; beyond that it holds rights (`domain.Rights`), which combine freely:

| Right | Permissions |
|---|---|
| work | card write (own cards), question ask, decision propose, note write, comment write |
| ready | card ready: any backlog card to ready, its own included; creating a task or story already in ready, except a child of a story past backlog |
| triage | card triage, without taking over claims; reworking another actor's decision proposal |
| answer | question answer in its own name (not relayed), with a reason and recorded for its owner (see Answers for a person), except a question asked from the same chat (base label) or its subagents |
| decide | accepting or rejecting a proposed decision for its owner, with a reason and recorded like an answer for a person (see Stories and decisions), except a proposal made from the same chat (base label) or its subagents, one that supersedes a decision still accepted, and any in the global project. It bundles no permission: nothing else that needs decision accept opens to the agent |

In a project an agent holds its project row's rights, its org rights where the org role applies (`Project.UsesOrgRole`), and its chat's grant for the base label of `X-Lorvik-Session`, all capped by the rights its owner's role there holds (`domain.RightsHeldBy`). No right gives an agent decision revoke, recording a decision as accepted at creation, `decide` on an answer, a claim override, agent register, or any admin or owner permission. A refused agent gets 403 `agent <name> lacks the <right> right in <slug>`, with a hint naming its chat.

Reference syntax: bodies may contain `[[card:42]]`, `[[card:web/42]]`, `[[note:slug]]`, `[[note:web/slug]]`, or any of them with a snowflake id (`[[card:7245123456789012345]]`). References are resolved to ids when the entity is saved and only resolved targets are stored, so backlinks never dangle and survive renames. A bare card number or note slug resolves in the source's own project first, then in the global project (`[[card:global/3]]` and `[[note:global/slug]]` name it explicitly). There is no `org:` prefix. Backlinks carry `type`, `id`, `project`, `number` or `slug`, and `title`, filtered to what the caller may see.

Status mapping: `domain.ErrNotFound` 404; `ErrVersionConflict` 409 with `current_version`; `ErrClaimedByOther` 409; `ErrLockHeld` 409; `ErrNotClaimant` 403; `ErrInvalidTransition` 409; `ValidationError` 422 with `errors[]`; structural rule breaks (open children, wrong parent kind, closed story, frozen text) 409 with a hint; `ErrUnauthorized` 401; `ErrForbidden` 403; invalid cursor 400. The public sign-in routes also answer 429 and 503 with a `Retry-After` header (`docs/requirements/login.md` 2.1a).

Semantics that both server and CLI rely on:

- Creating a task defaults to `backlog`; a question defaults to `ready`. `blocks` on a question creates `question blocks card` links and parks those cards in `waiting` if they were `ready` or `working`, releasing any claim; a `backlog` card is parked too, so the answer readies it, unless the linker is an agent without the ready right there; unlinking or dropping the question unanswered sends it back to `backlog` (#283).
- `next` skips cards with open blockers, claimed cards, cards whose parent is `dropped`, cards assigned to an actor other than the caller, and cards whose lane has a card in `working` or a live lock of the same name (see Branch and lane, Locks).
- Claiming moves the card to `working` and leases it for the project's lease (default 30m), or for the `lease` the caller states on `claim` or `renew` (`ClaimCard.lease`, a Go duration from 1m to 24h, cut to whole seconds; anything else is a 422 on `lease`, and so is any `lease` on `release`). A stated length belongs to the claim: it is `claim.lease` on the card, a `renew` that states one ends the claim exactly that long from now, and later renewals keep it until the holder states another or the claim ends. Any request renews leases past their half; the sweeper releases expired claims (`card.claim_expired`, actor = the former claimant, written in the session `@unprompted`, payload `status`, `expired_at` and, when the claim had one, `session`) and returns the card to `ready`. Before a claim ends the sweeper writes one last call per expiry, `card.claim_ending`: five minutes ahead, or a quarter of the lease when that is shorter. Its actor is the holder, it is written in the session `@unprompted` so the holder's own inbox shows it, its payload carries `expires_at` and, when the claim has one, `session`, and in the inbox it wakes the chat that holds the card. Nothing answers it but a renewal, which moves the expiry and arms the next call.
- Answering a question with `decide=true` records an accepted decision card in the same project (title = question title, body = `## Context` with the question body, or `See the page.` when the body is empty and the question has a page, and `## Decision` with the answer, the same page, done, accepted by the answerer) linked to the question with `relates`, under the question's parent when that story is open; the `Location` header names it. Then `waiting` cards with no open blockers left move to `ready`, except that a card a question parked from `backlog` goes back to `backlog` when its last blocker was unlinked, dropped, or a question closed unanswered (#283).
- Relayed answers. An agent that heard the human's answer elsewhere (in chat) passes it on with `POST .../answer` and `relayed=true` plus a `note` saying where and when the human gave it. The question closes at once (done, `answered_by` = the agent, claim released, waiting cards unblocked), so blocked work moves on, and the note is posted as the agent's comment. The `card.answered` event payload carries `relayed: true`. An agent without the answer right answering without `relayed` is a 403 naming the answer right, with the hint `relay the human's answer: lorvik answer N "<answer>" --relayed -m "<where they said it>"`; `relayed` without a non-blank `note` is a 422 on `note`; `decide` from an agent is a 422 on `decide` (a decision needs a human). A user sending `relayed` or a `note` is a 422. A relayed question stays flagged (`relayed: true` on `Card` and `CardBrief`, listed by the `relayed` filter, counted in no one's `open_questions`) until a user answers it again, which records the user's own answer, same text or different. Then `answered_by` and `answered_at` become the user and now, the question stays done, and the `card.answered` payload carries `confirmed: true` and, when the answer changed, `previous` (the relayed answer); `decide` works as for any answer. A done question answered by a user, and a dropped question, stay refused (409).
- Answers for a person. An agent answering under the answer right (no `relayed`) sends a `note` saying what the answer rests on (a decision, a requirements section, a person's words on a card); a blank one is a 422 on `note`. The question closes at once as with any answer, the note is not posted as a comment, and the card carries `behalf`: `for` (the agent's owner), `reason` (the note), `session` and `session_name` (the chat it answered from) and `kept_at`, absent until that person has looked. `behalf.by` names the agent. `card.answered` carries `for` (an actor) and `reason`. `POST .../keep` by that person sets `kept_at` and writes `card.kept`; nothing else on the card changes. Until then a user with question answer may answer again, as on a relayed question: their answer replaces the agent's, `behalf` is cleared, and the event carries `confirmed: true` and, for a change, `previous`; cards that moved on are not parked again. A kept question is settled like one a person answered (409). The `answered_for` filter lists what waits for a person. A verdict under the decide right is recorded in the same fields (see Stories and decisions).
- Questions for a person. A question carries `for_person` when only a person may answer it: set at creation (`CreateCard.for_person`, question cards only, else 422; `card.created` then carries `for_person: true`) or later with `POST .../for-person` on an open question. Marking is for the actor that asked it, an agent holding the answer right, or a user with question answer; an agent sends a `note` saying why (422 without), posted as its comment. While it is set, an agent's own answer is a 403 with the relay hint, whatever rights it holds; a relayed answer and a person's answer are unchanged. Only a user with question answer clears it (`clear: true`; 403 for any agent). Both write `card.for_person` with `set` true or false. Marking twice, clearing an unmarked question, or marking a closed one is a 409; a card that is not a question is a 422.
- Moving a question to `done` with the transition route is a 409 for agents (a question closes by its answer) with the same relay hint; users and dropping are unchanged.
- Dropping as `duplicate` requires `duplicate` (the surviving number) and records a `duplicates` link.
- A reply is a comment by someone else, newer than the last time the caller wrote on a card (create, edit, transition, answer, comment) or opened it (`POST .../seen`). `GET /projects/{slug}/replies` lists one entry per such card with the newest reply and the count of unseen ones.
- Every mutation appends one event in the same transaction. Events carry type, project, actor id, subject (type, id, number) and a payload with the subject's `title` and the facts of the change; clients render the sentence.
- `Card` carries `closing_note`: the `note` given with the move that made it done or dropped, kept until it is reopened, so a fold brief reads it without paging events. `CardBrief` also carries `drop_reason` (set when the card is dropped), `relayed` (set on a question whose answer an agent relayed), `for_person` (set on a question only a person may answer), `behalf` (set while the card stands as an agent settled it for a person), `closed_at` (set when it is done or dropped) and `fold` (`into`, `at`, `by`, the same object as `Card.fold`), each omitted when unset, so lists can word decisions and show fold state without a read per card.
- Every `card.status_changed` payload carries `kind`, the card's kind word (`task`, `question`, `story`, `decision`), beside `from`, `to` and the optional `drop_reason`, `note`, `duplicate_of`, `blocked_by`, `unblocked_by`, `by_child`, `cascade_of` and `superseded_by`. Events recorded before `kind` was added lack it.
- Events record the session label of the request that wrote them (`actor_session`, empty when none was sent; not part of the `Event` wire type). The inbox drops an event only when both its actor and its session are the caller's, so a lead sees what its subagents (same agent, other session) did, and two chats of one agent see each other. The CLI keeps one cursor per token and session.
- Events about a link between a global card and a card of another project (`card.linked`, `card.unlinked` and the `card.status_changed` a `blocks` link causes) belong to that other project, whichever side the link was made from, so a reader who cannot see that project never sees them. Card detail drops links and blockers in projects the caller cannot see.
- The inbox cursor is the client's: send the last `cursor` you stored, store the one you get back. Without `project` it is the newest event examined, including your own, so the next call starts past them. With `project` it stops at the last event returned (or stays put when nothing is new), so events in other projects are never skipped.

## Stories and decisions

Card kinds are `task`, `question`, `story` and `decision`. Status words are `backlog`, `ready`, `working`, `waiting`, `done`, `dropped`. Allowed moves by kind (`domain.CanTransition`):

| From | Task and question | Story | Decision |
|---|---|---|---|
| backlog | ready, dropped | ready, dropped | not used |
| ready | backlog, working, waiting, dropped | backlog, waiting, done, dropped | done (accept), dropped (reject) |
| working | ready, waiting, done, dropped | ready, waiting, done, dropped | not used |
| waiting | ready, working, dropped | ready, done, dropped | not used |
| done | ready | none (closed is closed) | dropped (revoke) |
| dropped | ready | none | ready (re-propose, from rejected only) |

A decision's illegal edge is a 422 on `status` (a claim or `working` is a 409). A story is never claimed and never moved to `working` by hand (409, hint "a story is not worked: start one of its children"); it goes working when a child starts. Stories never reopen and a closed story's children never leave it.

Decisions are cards of kind `decision`. Created `ready` they are proposals (any member); created `done` they are recorded as accepted, which needs decision accept and a user (403 otherwise). Status maps to the old words: proposed is ready, accepted is done, rejected is dropped with `drop_reason` `rejected`, revoked is dropped with `revoked`, superseded is dropped with `superseded`. `drop_reason` `rejected` is required to drop a ready decision, `revoked` to drop a done one, and both, with `superseded`, are refused on other kinds (422); `superseded` is never accepted from a client. Accepting, rejecting and revoking need decision accept and a user; the proposer or a reviewer may re-propose a rejected decision (the acceptor is kept on revoke). An agent holding the decide right accepts or rejects a proposal for its owner (decision #384): the transition needs a `note` saying what the verdict rests on (422 on `note` without), `accepted_by` is the agent, the card carries `behalf` as an answer for a person does, and `card.status_changed` carries `for`. It is refused (403) for a proposal made from the same chat (base label) or its subagents, for one that supersedes a decision still accepted, and in the global project. The owner keeps the verdict with `POST .../keep` (`card.kept` with `kind` `decision`). A revoke or a re-proposal clears `behalf`; by a user, while the verdict was not kept, its event carries `settled_by` and `settled_by_session`. Supersession clears `behalf` too. `Card.decision` carries `accepted_by`, `accepted_at`, `supersedes` and `superseded_by` (the last once the successor is done, and afterwards for as long as the old decision is dropped as `superseded`, even if the successor is later revoked). `CreateCard.supersedes` names the accepted decision in the same project that a new decision replaces; it is a link kind of its own (`supersedes`, new to old) that cannot be sent to the link routes. When the successor becomes done, the old decision moves to dropped(`superseded`) in the same transaction and gets a `card.status_changed` event with `superseded_by`; if it is no longer done (revoked meanwhile) it is left alone, and a decision already superseded takes no second successor (422 on `supersedes`). `applies` links run from a decision to a card, across projects only through the global project.

Stories hold tasks, questions and decisions one level deep: a parent must be a story and a story has no parent (409 with a hint). A story in `backlog` or `ready` goes `working` when its first non-decision child is claimed or started. `Card.progress` (`done`, `total`) counts done and dropped children over all children and is filled on the single-card read of a story. Closing a story (`done`) needs every child done or dropped (409 listing the open numbers) and `fold` (`into` the path of the requirements document, or `none: true`; both or neither is a 422 on `fold`). The fold is stamped on the story and every child (`Card.fold`: `into`, `at`, `by`; `into` is empty for none) and a `card.folded` event is appended for the story. Dropping a story with open children is a 409 unless `cascade` is true, which drops them with the same reason (decisions as `rejected`; `obsolete` when the story's reason is `duplicate`, since the children duplicate nothing), releases their claims, and marks their `card.status_changed` events with `cascade_of`; `cascade` on other kinds or other targets is a 422. A card with no parent may carry the same `fold` when it moves to done: it is stamped on that card alone and a `card.folded` event is appended, and a card that is already folded, has a parent or moves anywhere but done is a 422 on `fold` (hint "fold the story instead" for a card with a parent). Without a `fold` such a card stays unfolded and is folded later with `POST .../fold`; `GET /projects/{slug}/unfolded` lists those waiting.

## Global project

Every org has one global project (`Project.scope` is `global`; every other project is `project`), created with the org: slug `global`, name `Global`, visibility `org`, concurrency `parallel`. Org-wide notes live there; `-p global` addresses it. The slug `global` is refused for any other project (422), and archiving it is a 409. An actor with an org role has that role in it; an actor with no org role but an active role in any project of the org reads it as a viewer; writes need member or above, so a project-only agent reads but does not write there. `GET /projects` lists it first.

## Project concurrency

`Project.concurrency` is `parallel` or `serial` and is always present. New projects are `parallel`. `PATCH /projects/{slug}` takes `concurrency` (`UpdateProject.concurrency`, same permission as the other project fields, users only). It is advice for the lead agent's skill: `parallel` means fan child cards out to subagents when the harness can, `serial` means work them in order. The server does not enforce it.

## Branch and lane

Two optional text fields on `Card` and `CardBrief`, omitted from the JSON when unset.

- `branch`: the git branch the work is on. At most 200 characters, no whitespace. Set with `PATCH` (`UpdateCard.branch`); an empty string clears it. `lorvik start N --branch b` is a claim followed by that `PATCH`.
- `lane`: a short tag (at most 40 characters, no whitespace or commas, for example `schema`, `generated`, `goldens`, `web`) naming a resource that cannot take two concurrent edits. Set on create (`CreateCard.lane`) and with `PATCH` (`UpdateCard.lane`, empty clears). Surrounding whitespace is trimmed.
- `next` does not offer a card whose lane has any card in `working` in the same project, or whose lane is the name of a live lock in the org (see Locks). When it returns 404 and ready cards exist that were held back only for that reason, the problem body also carries `waiting_cards` (how many) and `busy_lanes` (the lane names, sorted); otherwise both are absent.

## Locks

A lock is a named, org-scoped lease on a shared resource (a generated file, a schema, a port) that two agents must not touch at once. Every agent sees every live lock: `GET /locks`, and `locks` on the inbox.

- Name: 1 to 40 characters of `a-z`, `0-9`, `-` and `/` (`domain.ParseLockName`); escape a slash in the path as `%2F`. Purpose: 1 to 200 characters. Lease: `ttl_seconds` 60 to 3600, default 600; anything else is a 422 naming the field.
- `PUT /locks/{name}` (`AcquireLock`: `purpose`, `ttl_seconds`, optional `card` with the `project` slug that numbers it, since card numbers are per project; a card that does not exist is a 422) answers 201 with the `Lock` (`id`, `name`, `holder`, `session`, `purpose`, `card`, `project`, `acquired_at`, `expires_at`). The session is `X-Lorvik-Session`. Needs the member role in the org or in any project the caller can see; viewers and read-only tokens get 403.
  - No row: the lock is created.
  - A row whose lease lapsed: it is taken over in place, writing `lock.expired` (actor = the former holder) then `lock.acquired`.
  - A live row held by the same actor in the same session: the call renews it from now with the new purpose and card, keeps `acquired_at`, and writes no event.
  - Any other live row: 409 `conflict` with the detail `lock held: <name> is held by <kind> <actor id> (session "<session>") for "<purpose>", <n>s left` and the hint `wait, or pick other work`.
- `POST /locks/{name}/renew` (`RenewLock`: `ttl_seconds`) sets the expiry to now plus the lease. Only the holding actor in the holding session may renew; anyone else gets 403, and a lapsed lock is a 404. Renewal is explicit only: no other request renews a lock, unlike claims. It writes no event.
- `DELETE /locks/{name}` deletes a live lock. The holder may release it from any session. A user with card triage (reviewer or above) may release another actor's lock with `?force=true`; everyone else gets 403, agents included. A lapsed lock is a 404.
- Events, all with subject type `lock` and no project: `lock.acquired` (payload `name`, `purpose`, `ttl` in seconds, `card` number when set), `lock.released` (payload `name`, `forced`, and `holder` when forced) and `lock.expired` (payload `name`, `holder`, `purpose`; actor = the former holder). The sweeper deletes lapsed locks each tick and writes `lock.expired` for each.
- `next` withholds a ready card whose `lane` equals the name of a live lock in the org, and lists that lane in `busy_lanes` on the 404, like a lane with a working card.

## Card list filters

`GET /projects/{slug}/cards` combines these with AND, on top of `status`, `kind`, `parent`, `mine`, `open` and `q` (`GET /cards` takes `lane`, `no_lane`, `no_story`, `relayed` and `answered_for` too):

| Parameter | Value | Matches |
|---|---|---|
| `created_after`, `created_before` | RFC 3339 | `created_at` in `[after, before)` |
| `updated_after`, `updated_before` | RFC 3339 | `updated_at` in `[after, before)` |
| `closed_after`, `closed_before` | RFC 3339 | `closed_at` (done or dropped) in `[after, before)`; cards never closed never match |
| `lane` | a lane name | cards carrying that lane; a 422 together with `no_lane` |
| `no_lane` | bool | cards with no lane |
| `relayed` | bool | questions whose answer an agent relayed (kind question, done, `cards.answer_relayed`) |
| `answered_for` | `me` or a user id | cards an agent settled for that person which they have not kept (`behalf.for`, no `kept_at`) |
| `no_story` | bool | cards that belong to no story: no parent, and not a story themselves; a 422 together with `parent`. With `lane` or `no_lane` it lists a map box (`lane:<name>` or `lane:`), the same cards `map/groups` counts |
| `assignee` | actor id, `me` or `none` | assigned to or claimed by that actor; `none` means neither assigned nor claimed |
| `priority` | comma separated `low,normal,high,urgent` | any of them (repeating the parameter keeps only the first value) |
| `sort` | `created`, `updated`, `priority` or `number` | omit for board order (status, priority descending, number) |
| `desc` | bool | reverses `sort`; a 422 without `sort` |

Sorts run ascending and break ties by number in the same direction, so `sort=priority&desc=true` lists urgent first. `sort` is a 422 together with `q`, whose results are ranked. Keyset cursors work under every sort and carry it; a cursor is valid only for the `sort` and `desc` it came from.

Example: `GET /projects/lorvik/cards?status=ready&assignee=none&priority=high,urgent&created_after=2026-10-16T00:00:00Z&sort=created&desc=true`.

`GET /notes` takes `created_after`, `created_before`, `updated_after`, `updated_before` (same semantics) and `author` (actor id or `me`: the creator of a note). Its order is unchanged.
