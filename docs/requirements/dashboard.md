# Dashboard navigation, scope and access display

Everything in sections 1 to 7 is implemented and checked against the code named in it, except where a line says otherwise. Code: `web/src`. The server contract the pages call is in `docs/api.md` and `docs/requirements/board.md`.

## 1. Purpose

The dashboard is the human side of Lorvik. This document fixes the conventions that span its pages: how a page is scoped to projects, how a card opens without leaving the page the reader is on, how a child relates to its story on screen, and how an agent's access is described. The pages themselves (board columns, forms, strips) are not specified here.

## 2. Behaviour

### 2.1 The project switcher and the scope of a list

- The header holds the project switcher. The selected project is kept per browser (`lib/projects.ts`, `projects.current`) and is set from the route whenever a route carries a `slug` param (`router.ts`).
- Switching project keeps the current section (`components/AppHeader.vue`, `switchTo`). On the board or activity route it navigates to the same route for the new project; on a card page it goes to the new project's board; on every other page it only changes the selected project and the page reloads its data.
- Notes, Decisions, Stories and Activity carry one scope control (`components/ScopeSelect.vue`): two pressed-state buttons, the selected project shown by name and "All projects". There is no separate Global choice: the global project is picked in the switcher like any other.
- The scope lives in the URL as `?scope=all`. An absent parameter means the selected project. Any other value reads as the selected project. With no project selected the effective scope is all and the project choice is disabled (`composables/useListScope.ts`).
- Changing the scope replaces the history entry and keeps the page's other query params. A pasted URL therefore shows the same scope to the recipient, whatever project they have selected.
- Picking a project in the switcher on one of these pages drops `?scope=all` and keeps the other query params, so the list shows the project just picked (`components/AppHeader.vue`). On Notes, Decisions and Stories this replaces the history entry like a scope change; on Activity it is part of the move to the new project's page. Decided by the owner on #410.
- Requests: Notes sends `project=<selected>` or omits it; Decisions and Stories send `project=<selected>` or `project=all` to `GET /cards`; Activity sends `project=<slug>` or omits it on both `GET /events` and the event stream, and restarts both together when the scope or the project changes. Rows in all scope show the project slug.
- The Stories page's unfolded-work section follows the scope: in project scope it lists the selected project's unfolded done cards; in all scope it is replaced by one line asking the reader to pick a project.

### 2.2 Opening a card without leaving the page

- The Board, Stories and Decisions pages open a card in a side panel over the page (`components/card/CardPanel.vue`); the list underneath keeps its filters, rows and scroll, and reloads on card events from the stream, so a verdict or move made in the panel shows in the row behind it without a refresh.
- The open card lives in the URL (`composables/useCardPanel.ts`): `?card=N` and, when the card is not in the page's own project, `?cardProject=<slug>`. The board omits `cardProject` for its own cards (`/p/lorvik?card=5`); Stories and Decisions have no project of their own and always carry it (`/stories?scope=all&card=3&cardProject=global`). A pasted URL opens the page and the panel.
- Opening pushes a history entry, so Back closes the panel. Closing (Close button, Escape, backdrop click) replaces the entry, so Back after closing leaves the page rather than reopening the panel.
- A click on a card link inside the panel swaps the panel to that card, in the same or another project, and pushes, so Back returns to the previous card. When the previous history entry is a panel, the panel header shows a Back button; Backspace outside a text field, or the browser's Alt+Left, does the same. Escape always closes; the Close button shows the Esc key. A click on the card already shown does nothing. A modified click (Ctrl, Cmd, Shift, Alt, middle button) and "Open as page" open the full card page `/p/<slug>/cards/<n>`, which stays the canonical link for pasting into chat.
- Cards from another project offered on the board by the Awaiting-you and Replies strips open in the panel the same way.
- A new card is written in a second side panel on the same shell (`components/SidePanel.vue`, `components/card/NewCardPanel.vue`, the form in `components/card/AddCardForm.vue`). The Ready column's "Add card" button (members and above) opens it as "New card"; the Decisions page's "New decision" button opens it as "New decision" with the decision kind preset and a project select. Its open state is local to the page and not in the URL. Escape, a backdrop click and Cancel close it without creating. Add creates the card in ready, closes the panel, reloads the list and opens the created card in the card panel (`?card=N`). The keyboard layer has no key for it.
- A new project is made in the same side-panel shell (`components/NewProjectPanel.vue`, the form in `components/NewProjectForm.vue`). The Projects page's "New project" button opens it and is shown only to signed-in people (not agents) with the org admin role or above; for them an org with only its global project also says so under the page title, and for everyone else the line says to ask an admin. Fields: Name (required, focused), Slug (follows the name, lowercased with other characters as hyphens, until the person types in it, and again once they empty it; what they type is lowercased), Description (optional) and Visibility (Org default, Everyone in the org, Private). The server's slug rule is authoritative and its message shows in the form (`POST /projects`). Create reloads the project list, makes the new project the current one, closes the panel and opens its board. Escape, a backdrop click and Cancel close it without creating. Its open state is local to the page and not in the URL.
- Ctrl+Enter or Cmd+Enter sends every editor that has a send button, as that button does and only while it is enabled (not busy, text not empty): the new-card body (Add), the comment box (Post), the answer (Submit answer), the note body (Save), the new project's description (Create project) and the comment prompt (`lib/sendKey.ts`, `sendOnModEnter`). A plain Enter adds a line. Each editor says so beside the markdown hint ("Ctrl+Enter posts.", "adds.", "sends.", "saves.", "creates."), always as Ctrl.
- The Replies strip (`components/Replies.vue`) is one wrapping line: "Replies to you N", then a chip per card with replies, newest first, showing `#N`, the title truncated, and `+M` when more than one reply is unseen. The chip's tooltip reads "<who>, <when>: <first line of the newest reply>". A plain click opens the panel, a modified click the card page. Opening the card clears its chip once the panel closes. "Mark all read" beside the heading marks every card with replies seen (`POST /projects/{slug}/replies/seen`), which clears the strip (#291). With no replies the strip is not drawn. The Map shows the same strip under its Awaiting you strip, at most a fifth of the view's height, scrolling past that. The card's board tile carries a "New reply" badge for as long as its chip shows.
- What waits on the viewer is the one filled magenta plate on the page, reserved for that (`.needs-plate`, `.needs-frame`). On the board a human reviewer sees it on a tile: "Needs you: accept or reject" on a proposed decision, "Needs you: answer" on an open question, "Needs you: decision #91" or "2 questions" on an open story holding them. A card assigned to someone else does not count as the viewer's (`awaitsHuman` in `lib/cards.ts`). A story's page heads its children with "Waiting on you" and a link to each, since Accept, Reject and the answer form live on those cards; a viewer who cannot settle them reads "Waiting on a reviewer".

### 2.3 Moving a card from the panel

- The transition bar (`components/card/TransitionBar.vue`) offers only the moves the server's per-kind table allows, mirrored in `lib/cards.ts` (`allowedMoves`); the server stays the authority and a 409 reloads the card.
- Done on a task or question in ready or waiting starts it first (which claims it for the clicker) and then finishes it, two calls, as `lorvik done` does. Done on a task or question with no parent reads Done… and asks for the fold, optional: a document path or "No contract change" sends it, and leaving both empty closes the card unfolded (button Mark done). A card with a parent keeps a one-click Done. Backlog has no Done: move it to ready first.
- Drop appears only where the table allows dropped: never on a done or dropped card. Reopen appears on a done or dropped task or question, never on a story.
- A decision's Accept, Reject and Revoke need a human reviewer; Re-propose on a rejected decision is offered to a reviewer or to the proposer with the member role.
- Every move the card offers stays visible as a button with an icon and its key from 2.9 (`s` Start, `r` Ready or Reopen, `w` Waiting, `b` Backlog, `d` Done or Done…, `x` Drop…), and each carries `aria-keyshortcuts`. The forward move is the one cobalt button: Done while the card is working, else Start, else Ready; Reopen on a closed card. A story's status follows its children, so Ready is its cobalt button only in backlog; once every child is settled (`progress.done == progress.total`, at least one child) Done… is, and in between it has none. Drop… sits apart at the end of the row. A decision's verdict buttons carry icons and no keys.
- The panel header (`components/card/CardDetail.vue`) reads top to bottom: the parent story as a link, the card's number with its status, kind and priority (normal priority is not shown), the title, then the assignee and claim, branch and lane (each an icon and its value), then "created <when> by <who>" and "last activity <when>": the newer of the card's update and its latest event, since a comment writes an event without touching the card (the version is the tooltip). They used to sit in a closed Details disclosure, where the owner did not find them (2026-11-08). Open blockers and "blocked by" links form one "Blocked by" list; every other relation gets one heading over its cards. Recent events are a closed disclosure with their count. The dialog is named by the card's title.
- A card an agent settled for a person (`behalf`, set on a question's answer or a decision's verdict) shows, in the panel and on the card page, a block headed "Answered by <agent> (<chat name, label>) for <person>" ("Accepted by" or "Rejected by" for a decision), with the answer, "Reason: <reason>" and "Not looked at yet." (`components/card/BehalfNote.vue`). Keep, shown only to the person it was for, calls `POST .../keep`; once kept the block reads "Kept <time>" and offers nothing more. Change, on a question for a human reviewer, opens the answer form, whose answer replaces the agent's; on a decision a line points to Revoke (accepted) or Re-propose (rejected) in the transition bar. A 409 on Keep reloads the card.
- A question with `for_person` carries a "for a person" mark beside its kind, and a human reviewer sees "Let agents answer it", which calls `POST .../for-person` with `clear: true` (`components/card/ForPersonClear.vue`).
- Status-change events name the kind: "accepted decision #8", "rejected decision #8", "revoked decision #8", "moved story #1 from ready to working".

### 2.3 A child and its story

- A card with a parent shows, as the first line of its detail, "← Story #S <title>" linking to the story (`components/card/CardDetail.vue`). The title is fetched with `GET /projects/{slug}/cards/S` after the child loads; until then, or if that fails, the line reads "← Story #S".
- In the panel that link swaps the panel to the story and Back returns to the child; on the full card page it opens the story's page. The story's own detail lists its children grouped by status, with progress, so a child is always one click from its story and back. The hierarchy has two levels, so there is no deeper trail.
- There is one panel, never a stack: a second pane would cover the first at laptop widths and two modal dialogs need coordinated focus and scroll locking. Rejected on 2026-10-31.

### 2.4 What an agent may do, on the Access page

- Each agent row carries a summary instead of raw grants (`views/AdminView.vue`):
  - With an org membership: "Shared projects:" with its org-wide rights, then "Includes Global. Private projects need their own access.", then "Project access:" followed by one small table (`components/RightsGrid.vue`): the right names Work, Ready, Triage, Answer and Decide once as column headings (each titled with the right's tip), one row per binding to a non-global project with its slug in monospace, and a centred checkbox per cell (the locking rules live in `lib/rights.ts` and are shared with `components/RightsChecks.vue`, the inline checkboxes of the other forms; labels and tooltips also in `lib/rights.ts`; labels and tooltips in `lib/rights.ts`; Decide lets an agent accept or reject a proposed decision for its owner). A change calls `PUT /agents/{id}/projects/{slug}` with the whole set; the last right cannot be unchecked (Remove takes the project away). A right the signed-in user's role there cannot give (work needs member, the others reviewer) is disabled, checked or not, because the server checks the whole set against the giver.
  - Chats: under the bindings, "Chats (N)" lists the agent's sessions from `GET /agents/{id}`, one line per chat: label in monospace, last seen (or "never seen" for a chat that only holds a grant), and what differs from the agent, "Same as the agent" or "+ <rights> in <project>" per project, plus "On duty in <project>, ends ..." with End duty for each duty. The note that a chat's grant covers its subagents (`-c<n>`) and that `lorvik status` shows a chat's label is the heading's tooltip, marked with a "?". Chats not seen for 24 hours, or never, fold under "N older chats" at the end of the list; when every chat is older, they all show. A "Change" button on the line opens a rights table for the chat under it, with a row per bound project and the same checkboxes: rights the agent already holds there are checked, disabled and titled "From the agent"; checking another calls `PUT /agents/{id}/sessions/{label}/projects/{slug}` with the chat's extra rights, and unchecking the last calls `DELETE`. A change sends the grant's end and instructions again, so a chat on duty keeps them. Projects the agent reaches only through its org membership get no chat checkboxes.
  - Put on duty (`components/DutyForm.vue`): a chat of an active agent the caller may manage has a quiet "Put on duty" button on its line that opens a form under it.

    | Field | What it is |
    |---|---|
    | Project | The agent's project access and, for an agent with an org membership, every shared project the caller sees. |
    | Ends | A date and time, 8 hours from now by default. Required and in the future, so a duty is never open-ended. |
    | Instructions | The owner's words to the chat, up to 4,000 characters. |
    | may ready backlog cards | The ready right. |
    | may accept or reject decisions | The decide right. |

    A tick the agent already holds in the project is checked and locked ("From the agent"); one the caller's role cannot give is disabled. A project the chat already has a grant in fills the instructions and the ticks from that grant, so a duty is extended without losing them; choosing a project without a grant after one that has it empties them, so one project's instructions and rights never go to another. The instructions are in `GET /agents/{id}` only for a caller who may manage the agent (`agents.md` 2.6), who is also the only one offered the form. Submitting calls `PUT /agents/{id}/sessions/{label}/projects/{slug}` with `answer`, the ticked rights the agent does not hold itself, the chat's other extra rights, `ends_at` and `instructions`. When the caller's role cannot give that set, the button is disabled and a line says the reviewer role is needed. A grant that has an end shows under its chat as "On duty in <project>, ends <time>" with its instructions and "End duty", which is the same `DELETE` as taking the chat's rights back.
  - With bindings only: the same "Project access:" table, then "Global: read only, included automatically."
  - With neither: "none yet, it cannot act anywhere".
- Org members (the list above Agents): an agent row shows its org-wide rights instead of a role select, since the server refuses a role for agents. An admin gets the rights checkboxes (`RightsChecks` with no project, so `canGiveRight` checks the org role; the last right cannot be unchecked) and a change calls `PUT /members/agent/{id}` with `{rights}`; anyone else sees the rights as text.
- Wording: the org role is called the shared-project role; a binding is project access; the form is "Add project access" with rights checkboxes (default Work) and an "Add access" button, inside a closed disclosure "Give access by hand", since agents mostly join projects themselves (2.14).
- The Agents intro says agents hold rights per project and per chat and accept or reject decisions only for their owner, with the decide right. A second line says what Revoke and Remove do.
- Agents load with `all=true`. A live agent the caller may manage has Revoke and Remove; a revoked one has Restore and Remove. Revoked agents the caller may manage sit in a last group, "Revoked agents", with a line saying what Restore and Remove do; other people's revoked agents are not shown to a non-admin. Each of the three buttons carries a tooltip saying what happens (`TIPS.revoke`, `TIPS.restore`, `TIPS.remove`). Remove asks for confirmation first, since it cannot be undone. Routes and effects: `agents.md` 2.7.
- Project members (`components/ProjectMembers.vue`): an agent row shows the rights checkboxes instead of a role select (plain text without manage, and in the global project); picking an agent in the add form swaps the role select for them.
- The caller's own agents come first. When anyone else's are listed too (an admin sees them all), the two groups are headed "Your agents" and "Other people's agents".
- The harness badge is left out when the name already says it: the name is the harness or starts with `<harness>@`, as every agent the CLI registers does.
- The form's project select omits the global project. A binding to it changes nothing about what the agent may do there, so the page does not offer one. Existing bindings to the global project are not shown as grants.
- The Projects page shows the global project's memberships read-only with one line saying why (`components/ProjectMembers.vue`, prop `global`): the shared-project role, or viewer, applies there for everyone.
- The Agents section states the cap: agents hold at most reviewer and never answer questions or accept or reject decisions.

### 2.5 Running now

- The board shows a "Running now" strip above the Awaiting-you strip (`components/RunningNow.vue`) with one row per live lock of the org, from `GET /locks`. Locks are org-wide, so the strip is the same on every board. With no live lock the strip is not drawn.
- The strip is the ink band (`.plate`). A row shows the lock name in monospace, the holder's name, the holder's session in muted text, the purpose, the card as a `#N` link when the lock names one, and the time left as the band's amber figure. The link goes to the card in the lock's own project and opens in the panel like any card link (2.2).
- Time left is the distance from now to `expires_at`: whole minutes from one minute up ("7m left"), seconds below that ("42s left"). It is recomputed every 30 seconds without a request. A lock whose lease has run out is dropped from the strip at the next tick.
- Release is shown to a signed-in human with the reviewer role or above in the org or in the current project. It asks for confirmation, then calls `DELETE /locks/{name}?force=true` and reloads the strip. Agents never use the dashboard, so there is no agent variant; the server enforces the role regardless.
- Refresh: the strip subscribes to the event stream without a project filter and reloads 400 ms after a `lock.acquired`, `lock.released` or `lock.expired` event. Lock events carry no project and are delivered on every stream. It loads once on mount.
- Event wording, on Activity and wherever events are listed (`lib/events.ts`): `took lock <name> for "<purpose>"`, `released lock <name>`, `force-released lock <name> (held by <holder>)` when forced, and `lock <name> expired (held by <holder>)`. A lock event's subject is a lock, so its row is plain text and links nowhere.

### 2.8 Signing in and granting access

The server contract is `docs/requirements/login.md` 2.2 and 2.4; this is what the pages do with it.

- Login page (`views/LoginView.vue`): on mount it reads and expires the `lorvik_handoff` cookie (`takeHandoff` in `lib/auth.ts`, expired with Path `/login`). With a secret in it, the page keeps it in memory, loads `/me` with it, stores the session and goes to `next`; a failure shows in the usual error banner with Retry, and a 401 drops the secret. Without one it calls `GET /api/v1/auth/github`; when `enabled` is true a "Sign in with GitHub" button is shown above the token and password forms and navigates the browser to `/auth/github/start?next=<next>`. A failed call hides the button. `next` is used only when it starts with `/` and not `//`, else `/`.
- Login page with a stored session: the guard sends a signed-in user (token and `/me` both in memory) away from `/login`, so the page renders with a stored token only after a full page load (a GitHub callback redirect, a reload). When GitHub is enabled and `lib/auth` holds a token, the page loads `/me` (a 401 clears the session) and replaces the "Sign in with GitHub" button with "You are signed in as <name>" and two actions: "Link GitHub to this account" (users only; calls `POST /me/github-link` with `next` when the URL carries one, then navigates to the returned `url`, as the Access page does) and "Sign out first" (clears the session and shows the normal button). The token and password forms stay below and replace the session.
- The `error` and `login` query values render as a line under the title, with the texts of login.md 2.2 (`pending`, `denied`, `org`, `github`). Other values show nothing. `pending` names the org from `org_name` ("this org" when absent); `org` reads "This sign-in link names an org that does not exist."
- Choosing an org (login.md 2.2b): a sign-in that is not for one org answers with a sign-in token (scope `signin`, ten minutes), either as `token.scope === 'signin'` on the password answer or as a handoff secret on a `/login?choose=1` redirect. The page then keeps that secret in memory only and replaces the sign-in forms with: "You are signed in. Pick where to go."; the orgs from `GET /login/orgs` (a `member` org is a button with its name and role, an `invited` one reads "invited as <role>", a `requested` one is a plain row "<name>: waiting for an admin"); a "Create an org" form (one required name field, at most 200 characters); with no orgs, "You belong to no org on this server yet. Create one, or ask an admin of an existing org to invite your GitHub username."; and a quiet "Sign in as someone else" that drops the secret and shows the forms. A click on an org calls `POST /login/orgs/{id}/token` and then loads `/me` with the new token as any sign-in does; creating an org enters the new one the same way. A 401 from any of these calls drops the secret, shows the forms and says "That sign-in expired; sign in again." The raw org id field is gone from the password form.
- `/login?choose=1` (from "Switch or create org") makes the GitHub button go to `/auth/github/start?next=<next>&choose=1` and the password form send `choose: true`, so the choice is asked even when the person is in one org only.
- Deleting your account (#420, owner's answer on #417; login.md 2.4b): in "Your sign-in" on the Access page every person sees a danger button "Delete my account". It opens a dialog (`components/DeleteAccountDialog.vue`) that says what goes (the place in every org, the agents they created, revoked, the GitHub link and password, the tokens; it cannot be undone) and what stays (the name on past cards, comments and history, with "(deleted)" after it), then, on the Access page, what `GET /me/deletion` answers: each org that closes with the account ("Closes <org>: N projects, M cards.", #423, owner's answer on #422) and, when an org refuses it, "You are the only owner of <orgs>, beside other people. Make one of them owner on the Access page first." with the button kept disabled (a failed preview shows its error and a Retry button, and keeps the button disabled until it loads); and asks "Type your login, <login>, to confirm"; the red "Delete my account" button is enabled only when the input equals the login exactly. It calls `DELETE /me` with `{confirm}`; on 204 the session is cleared and the login page shows "Your account was deleted." (query `notice=deleted`, watched so the choice screen shows it too, then removed). A refusal (for example 409 for an org's only owner) shows the server's message and hint in the dialog. On the Create-an-org screen with no orgs, after a GitHub sign-in (not a password one, which asks to be added rather than invited by GitHub username), the hint "This GitHub account is not linked to any account on this server. If you already have one, sign in with it and link GitHub on the Access page instead." shows, and a "Delete this account" button, shown only then, opens the same dialog; the login to type comes from `GET /login/orgs` (`login`) and the call carries the sign-in token. A deleted person (`status: "deleted"` from `GET /actors`) reads "<name or login> (deleted)" wherever names show (`record()` in `lib/actors.ts`).
- Switching org: the Access page shows "Org: <name>" under its title with a "Switch or create org" button, and the command palette lists the same action. Both clear the session and go to `/login?choose=1`.
- Join link: on the Access page, admins see under the invite form, when GitHub sign-in is on, `<origin>/auth/github/start?org=<org id>` in a read-only field with a Copy button, and a line saying that people who sign in through it ask to join and are granted a role under "Waiting for access".
- Access page (`views/AdminView.vue`), admins only: members load with `all=true`. A "Waiting for access" group sits above the members list. A requested row shows the name, "asked to join", a role select (default viewer, roles above the viewer's own disabled), Grant and Decline. An invited row reads "Invited as <role>, has not signed in yet" with Revoke invite. Removed rows are not shown, and the members list itself shows only active rows for admins. The group is absent when nothing is pending.
- Below the members list, admins see "Invite by GitHub username": a login field (a leading `@` is dropped), a role select and an Invite button. A refusal from the server (unknown GitHub user, already a member) shows as the page's error banner. Viewers and members see neither the group nor the form and load `/members` without `all`.
- Event wording (`lib/events.ts`): `asked to join the org` for `membership.requested` (the actor is the requester) and `invited <name> as <role>` for `membership.invited`, the name from the payload's `actor` or `login`, the role when present; `restored agent "<name>"` (with "(pending approval)" when it waits) for `agent.restored` and `removed agent "<name>"` for `agent.removed`; `linked GitHub account <login> to their account` for `identity.linked` and `unlinked GitHub account <login> from their account` for `identity.unlinked`. `had a wrong password entered for their login` for `identity.signin_failed` and `had repeated wrong passwords entered for their login, up to a sign-in limit; tries over it are refused for now` for `identity.signin_refused` (the actor is the person the login belongs to). `deleted their account` for `user.deleted`.

### 2.9 Keyboard layer

- One document listener (`composables/useKeymap.ts`, installed in `App.vue`) serves every binding; components register theirs for as long as they are mounted, and the newest registration wins a key it shares. A binding never fires while the event target is an input, textarea, select or contenteditable element, and never on an Alt chord. `mod` is Ctrl, or Cmd on a Mac. A two-key sequence (`g b`) waits one second for its second key.
- Layers: a key press lands on the page, on the card panel (the open `<dialog data-keymap="panel">`), or on any other open dialog or popover (help, palette, prompt, context menu). Board keys fire on the page only, card keys on the page (focused tile) or the panel (open card), and no page or card key fires while another dialog or popover is on top. Escape closes the top dialog through its own cancel event, and Backspace in the panel goes back as in 2.2.
- General, from the header (`components/AppHeader.vue`): `?` shows or hides the help (`components/KeymapHelp.vue`), which lists every registered binding by group, one row per key and label; `mod+k` opens the command palette. `g b` Board, `g s` Stories, `g d` Decisions, `g n` Notes, `g a` Activity, `g p` Projects, `g i` Inbox; Board and Activity need a selected project. The header also has a Search button showing the palette's key and a keyboard icon button for the help.
- Board (`views/BoardView.vue`): `j` and `k` move focus to the next and previous tile in the column, `h` and `l` to the neighbouring column that has tiles, at the same row or the last one. With no tile focused, any of them focuses the first tile of the first column with tiles. The walk follows the tiles as drawn, so hidden and collapsed columns, the story filter and "load more" apply. Enter on a focused tile is its click and opens the panel; closing the panel returns focus to the tile.
- Card actions (`lib/cardActions.ts`, run by `composables/useCardActions.ts`): `s` Start, `r` Ready (Reopen on a done or dropped card), `w` Waiting, `b` Backlog, `d` Done, `x` Drop, `c` Comment. On the board they act on the focused tile; with nothing focused the key shows "Focus a card first". In the panel they act on the open card. A card offers only the moves `allowedMoves` gives for its kind and status, and only to a viewer with the member role in its project, as the transition bar does (2.3). Done on a task or question in ready or waiting starts it first (which claims it), then finishes it. A decision offers only `c`: its verdicts stay buttons in the panel.
- Before a move the card is read again, so the check uses its current status and the move carries its current version. A move the card no longer offers is not sent and shows why ("#N: Start is not offered on a task that is done"). A 409 shows the server's message and reloads the card in the panel.
- `x` asks for the reason (obsolete, duplicate with the card number, wontfix), an optional note and, on a story with open children, whether to drop them too. `d` on a story asks for its fold, required: a document path or "No contract change". `d` on a task or question with no parent asks for the same fold, optional (title Done, button Mark done); on a card with a parent it finishes in one step. `c` asks for the text. The prompt (`components/card/ActionPrompt.vue`) is a modal dialog over the page or the panel and returns focus to where it was opened.
- The outcome shows as a toast at the bottom right (`components/ActionToast.vue`, a manual popover, so it shows over the panel): "Commented on #N" for 3 seconds, an error for 8. A successful move shows no toast: the tile changes column and the panel its status. The open panel reloads after a move made by a key or the menu; the board reloads from the event stream (400 ms).
- Command palette (`components/CommandPalette.vue`), `mod+k` or the Search button: a modal dialog with one input. It lists the pages, filtered by name, and a "Keyboard shortcuts" entry. `N` or `#N` adds "Card #N" in the selected project first. Two or more other characters search `GET /search` across every project the viewer can read (at most 20 hits, 200 ms after typing stops; a stale answer never replaces a newer one). Card hits show "#N title" with project, kind and status; note hits show the title with "note" and the project. Up and Down move, Enter opens, Escape or a backdrop click closes. A card opens in the panel on Board, Stories and Decisions, by the URL rule of 2.2 (`panelQuery` in `composables/useCardPanel.ts`), and on its own page from any other page. A note opens its page. A failed search says so; pages and `#N` still work.
- Context menu (`components/card/ContextMenu.vue`) on a board tile: right-click, or the ContextMenu key or Shift+F10 on a focused tile, which opens it under the tile. It lists Open, Open as page and the card actions the tile's kind and status offer, each with its key. Up, Down, Home and End move; Enter runs; an action's letter runs it from the menu; Escape, Tab or a click outside closes. Focus returns to the tile, and a menu action is checked against the card's current state as a key is.

### 2.10 Look and speed

- One visual system (`src/tokens.css`, `src/base.css`, component classes in `src/style.css`): Inter for reading and controls (weights 400, 500 and 600) and Chivo Mono for what is copied or matched (card numbers, slugs, branches, lock names, code, counts; the `.ident` class), both self-hosted from `public/fonts` and preloaded in `index.html`; cobalt for live state and the one primary action per screen or dialog; magenta for what waits on the viewer; amber for figures on the ink band; 3px corners on every control, chip and surface (`--radius-control`, `--radius-panel`), with the status swatch the one square; rules instead of shadows except on floating layers (panel, dialogs, menus, toast). Light and dark follow `prefers-color-scheme`.
- A lane's name is shown without the word "lane" wherever its place, icon or tooltip says what it is: board tiles, the Stories list, the card panel, the map's boxes and the lane filter's options. The word stays where it names a field or a filter (the Lane field, "Edit branch and lane", "All lanes", "No lane", "Lane filter" on a hidden card) and in tooltips and screen-reader names (the owner, #438 and #439).
- Motion is a 120 ms colour change in `steps(1)` on controls and nothing else: no slides, fades or loading spinners. Loading lists show grey skeleton rows; empty board columns say what is absent ("Nothing parked.", "Nobody is working a card.").
- Every subscriber without a resume point shares one all-projects event stream (`lib/stream.ts`) and filters by project in the browser; a board with the panel open holds one connection instead of five. Activity, which resumes after its newest event, keeps its own.
- A page that is left ends its event streams and stops any polling (`pagehide`), because a page the browser keeps in its back/forward cache would otherwise hold its connections open and, with the limit of six per origin, stall the next page's requests. A page restored from that cache (`pageshow` with `persisted`) reopens them, each after the last event it had seen, so none is missed or shown twice. A stream that opened with no position reads the newest event's position once it is open (the request the polling fallback makes), so it has one to resume from before any event arrives.
- A resume position that names no event (the server's database was reset) is a 422 on `after`: the stream drops it and reconnects at the head, and polling does the same. The Inbox page does likewise with a stored cursor the server rejects, and reads from the oldest event.
- A card's comments and the revision history of a card or note load 50 at a time, newest first, with Load more for older ones (`composables/useHistoryList.ts`); the lists carry no count, so the button shows none. An event rereads the newest page and keeps the older ones already shown.
- Links only navigate (`.lnk`, underlined; `.lnk-quiet` for a feed row's sentence, underlined under the pointer). Anything that acts in place is a button: `.btn`, `.btn-quiet`, `.btn-icon` (square, always with an accessible name and a title) or `.btn-link` (inline text action, not underlined). Icons are Lucide, compiled into the bundle by `unplugin-icons` (only those imported ship, no runtime library) and hidden from assistive technology; collapsible board columns show a chevron.
- Written text: every multi-line field shown in full (card body, answer, comment, note body, project description, revision bodies) renders as markdown through `components/NoteBody.vue` (`lib/markdown.ts`: markdown-it with raw HTML off, `[[card:N]]` and `[[note:slug]]` as in-app links, other links open in a new tab). A place that cannot hold HTML (a tooltip, a one-line label) shows `markdownText`, the readable text of the same parse. Titles are plain text. Every editor for such a field says markdown works (`components/MarkdownHint.vue`).
- No redundant labels: a visible label appears only where the content would not be understood without it. The card's body under its title carries none (its heading is screen-reader only); a heading that only names what is already obvious is kept for screen readers with `sr-only`, not shown.
- Header (`components/AppHeader.vue`): Search, the keyboard help, Inbox and Sign out carry icons; the help and Sign out are icon-only buttons. Under 75rem the section links move to their own sideways-scrolling row with Sign out at its end, and the help button is hidden; under 85rem the search key hint and the user's name are hidden.
- Event rows on a card's own history name it "this card" (or "this decision") and do not link to it (`describeEvent` with `here`, `components/EventRow.vue`).

### 2.11 Working now

- A chat that has a name reads as `<name> (<label>)` wherever its label shows on its own: Working now, Running now and the Access page's Chats (`chatLabel` in `lib/actors.ts`). After a holder's name in the card panel, the brackets hold `<name>, <label>` (`holderChat`), as in `claude-code@box (billing migration, calm-lynx-4aa4)`. A chat with no name shows the bare label.
- On a board tile the chat leads and the holder follows, `billing migration · claude-code@box`, with the label in the chat's place when it has no name (#343 A). The line is one line cut at the tile's width, about 30 characters, so what is lost is the end of the holder's name; holder first, the holder's name alone filled the line and no chat was ever visible. The line's hover text is the full `Claimed (lease held) by claude-code@box (billing migration, calm-lynx-4aa4)`. A claim without a chat and an assignment show the holder's name alone.
- The Projects page opens with a "Working now" panel (`components/WorkingNow.vue`): a summary line ("5 chats of 2 agents and 1 person working in 2 projects"; a chat is one holder's session, agents and people are counted by identity), then one group per holder and session, each card as a `#N title` link with its project, how long ago it was claimed and the lease left. With nothing live it is one muted line.
- Each project row carries an "N working" badge counting the live claims in it.
- The data is `GET /claims`, the live claims of every project the viewer can see; a lease past its end is left out even before the sweeper deletes it. `lorvik who` prints the same list, grouped the same way, with the same summary line, so the panel and the CLI never disagree.
- Refresh: the panel re-reads 400 ms after a `card.claimed`, `card.released`, `card.claim_expired` or `card.status_changed` event, and a one-minute tick drops leases that ran out between events.

### 2.12 Searching the Board

- A search box at the right of the Board's toolbar (`components/SearchBox.vue`) matches tiles by number (`12`, `#12`) or title (`lib/cardSearch.ts`) and outlines them; the search is in the URL (`?q=`). A line under the box reads "1 of n" or "No matches"; Enter moves to the next match and scrolls it to the centre. Typing does not scroll the board. `/` focuses the box, Escape clears it.
- The server is asked as on the Map (map.md 2.3). A match with no tile is counted on a chip ("n more not shown", or "n not shown" with the "No matches" counter hidden when no match has a tile) that opens a list with the reason: its column hidden or collapsed, the story filter, or "Not loaded yet" (`lib/boardHidden.ts`). Choosing one clears the story filter if that hides it, shows and opens its column, pages the column up to 20 pages until the tile is drawn, then scrolls to it and focuses it; a card further down opens in the panel instead. Clearing the search gives the paged columns back their earlier length.

### 2.13 The page of a card or note

- A card or note may carry an agent-written HTML page (`page_bytes` above 0 on the card, note and their briefs). The card view (page and side panel) and the note view show it first, in a frame, fetched when the view opens and again when the version changes (`GET .../page`; `components/PagedBody.vue`).
- With a page and a body, two tabs: Page (selected) and Text (the Markdown). With a page and no body, the page alone, with no tabs and no empty body section. Without a page, the body as before. The tabs are a tablist: Left, Right, Home and End move between them.
- Above the frame a label row the page cannot change: "Page", its size, "Runs sandboxed" (the tooltip says it cannot see the session or reach the network, except approved script libraries) and Expand. Expand shows the page full viewport in a modal dialog (Esc or Collapse returns); the inline frame is replaced by a placeholder meanwhile, so only one copy runs.
- Sandbox (`components/PageFrame.vue`, `lib/pageFrame.ts`): `<iframe sandbox="allow-scripts" referrerpolicy="no-referrer" srcdoc>`, never `allow-same-origin`, so the page gets an opaque origin and cannot read `localStorage` (the sign-in token) or the dashboard DOM; no navigation, popup, form, modal or download flags. The srcdoc starts with a CSP meta: scripts and styles only inline or from `cdnjs.cloudflare.com`, `cdn.jsdelivr.net` and `unpkg.com`; images only `data:` and `blob:`; no fonts (system fonts only), no `connect`, media, frames, workers, objects, form actions or `<base>`; `webrtc 'block'` where the browser enforces it (Chrome 156 does not).
- Height: a small script in the prefix posts `{ lorvikPageHeight: n }` to the parent on load and on resize. The parent accepts only that exact shape from its own frame's window, clamps it to 240 to 4000 px, and never sends anything to the frame. The page cannot answer questions or change anything.
- A board tile with a page shows a small window icon in its id row ("Has a page"); the board and the map never render frames.

### 2.14 Agents asking to join projects

An agent asks to join a project (`POST /projects/{slug}/join`); four settings decide whether it gets in without asking: "always ask" from any of them wins, then "allow" from any, else its owner is asked. The dashboard holds the settings and the asking.

- Awaiting you (`components/AwaitingYou.vue`): for a signed-in human only, above the cards, one row per pending request of their own agents across all projects (`GET /agent-requests`): the agent's name, "asks to join <project> to <rights>" (the rights allowing gives, in words: "to work"), the agent's harness and machine, how long ago, and three buttons. Allow calls `PUT /agent-requests/{agent}/{slug}`. Deny calls `DELETE` on the same path; the agent is then refused when it asks again until its owner adds it on the Access page. "Allow in all my projects" first sets the agent to allow (`PATCH /agents/{id}`, `agent_join` allow), then allows this request. The rows count in the "Awaiting you" total. An agent caller never sees them. The list reloads 400 ms after an `agent.join_requested`, `agent.joined`, `agent.join_denied` or `agent.updated` event on the all-projects stream, and after each button.
- Access page, account switch (`views/AdminView.vue`): above the Agents list, for a human, the checkbox "Let my agents join my projects without asking". It reads `user.agent_join` from `/me` and calls `PATCH /me` with `allow` (checked) or `follow` (unchecked).
- Access page, per agent: each pending request of the caller's own agent shows on its row as "Asks to join <project> to <rights>", how long ago, Allow and Deny, the same calls as the Awaiting you strip; the page reloads after each. For an active agent the caller may manage (its owner, or an org admin) and a human caller, a select "Joining projects" above the access form: "Follow my settings", "Allow in all my projects" or "Always ask". It reads the agent's `agent_join` and calls `PATCH /agents/{id}`.
- Projects page (`components/ProjectAgentJoin.vue`): each project except the global one has a closed disclosure "Agents joining" above Members; opening it reads `GET /projects/{slug}` (`my_agent_join` is not on the list). A human sees "My agents here": "Follow my settings", "Allow without asking" or "Always ask" (`PUT /projects/{slug}/agent-join`). A human project admin also sees "Agents always ask here": "No, follow each owner's settings" or "Yes, every agent asks" (`PATCH /projects/{slug}`, `agent_join` follow or ask). The server enforces who may set what; a failed save reloads the stored values.

### 2.15 What an agent settled for you

A chat on duty (2.4) answers questions, and with the decide right accepts or rejects decisions, for its owner. Each one waits for the owner until they keep or change it; the rules are in `board.md` and `decisions.md`.

- Answered for you (`components/AnsweredForYou.vue`, under the Awaiting-you strip on every board and map; for a signed-in human only): what an agent settled for the viewer and they have not kept, from `GET /cards?answered_for=me&status=done,dropped` across projects (the first 50, each read in full for its answer and version). A row shows `#N`, the kind, the title and when it changed, then "Answered by <agent> (<chat name, label>)" with the answer below it, or "Accepted by" or "Rejected by" for a decision, and "Reason: <reason>". Keep calls `POST .../keep`; Change opens the card in the panel, where the answer form or Revoke and Re-propose do the change. It is hidden when empty, reloads 400 ms after a `card.answered`, `card.status_changed` or `card.kept` event on the all-projects stream and after Keep (a 409 on Keep reloads too), and a kept row disappears.
- Event wording (`lib/events.ts`): `kept the answer on` or `kept the verdict on` for `card.kept` (by its `kind`), `marked ... for a person` and `cleared the for-a-person mark on ...` for `card.for_person` (by `set`), and ` for <name>` after an answered event and after a decision's accept or reject that carries `for`.
- The same card in the panel and on its page: 2.2.

## 3. Rules

- The dashboard never widens access: every summary line on the Access page is derived from the rules in `internal/domain/project.go` (`Visible`, `EffectiveRole`). When those change, 2.4 changes with them.
- The URL is the source of truth for scope and for the open card. Components read it and write it; none keeps a shadow copy that could disagree.
- Opening something is a history event (push); closing it or changing a filter is not (replace).

## 4. Data

No tables. Browser storage (`lib/storage.ts`) is kept per org, because project slugs are unique only inside an org: every key below is built by `orgKey` in `lib/auth.ts` as `lorvik.<org id>.<name>`. It holds the selected project slug under `lorvik.<org id>.project`, the Board's hidden columns under `lorvik.<org id>.board.hidden`, the map's filters per project under `lorvik.<org id>.map.filters.<slug>`, and per project the view last open, Board or Map, under `lorvik.<org id>.view.<slug>`. `lorvik.token` and `lorvik.inbox.<org id>` are as before. When a session is set, keys from before orgs (`lorvik.project`, `lorvik.board.hidden`, `lorvik.view.*`, `lorvik.map.filters.*`) are copied under the signed-in org when it has no value of its own yet, and removed; the first org signed in to takes them. The selected project and the project list are read again whenever the signed-in org changes, not when the module loads. The view key: the header's Board link, `g b`, a card page's "Board" link and the project switcher open that view. Going to either view by the switch or a link that names it updates the key; an automatic pick (no key yet) does not, so it is decided again on each visit. Nothing else about navigation is stored.

## 5. API

The pages call existing routes only: `GET /cards` (`project=all` or a slug), `GET /projects/{slug}/notes` and `GET /notes` through the client's `notes()` with or without a project, `GET /events` and `GET /events/stream` with or without `project`, `GET /projects/{slug}/unfolded`, `GET /agents` and `GET /agents/{id}` for the Access page, and `GET /claims` for Working now (2.11), added for it.

## 6. Jobs

None.

## 7. Why it is this way

- Two scope choices, not three. A separate Global option let the header say one project while the list showed another. Rejected: a Global entry in each page's scope select. Decided in chat on 2026-10-31 after a Codex brainstorm (`tmp/local/ux-brainstorm-codex-2026-10-31.md`, not in git).
- The switcher keeps the section. Sending every switch to the board made Decisions, Stories and Notes feel like detours. Rejected: switcher always opens the board.
- The Access page describes effective access instead of listing grants, because a grant on the global project is accepted by the server and does nothing, so a badge for it promised access the agent did not have.
