# Requirements: projects, cards, stories and decisions

Everything in sections 1 to 7 is implemented and checked against the code and tests named in it, except where a line says "unverified". Intended changes are in 2.9 (none). Known defects are in 2.10. Decision-specific behaviour (body template, supersession, wording) is in `decisions.md`.

## 1. Purpose

Everything a team tracks is a card in a project. Cards have four kinds: task, question, decision and story. A story groups the cards of one piece of work and closes only when they are settled; closing it folds the result into the repo's requirements documents. Every org has one global project for what applies across projects. Roles, versioning, the error format and reference syntax have one home each (`docs/api.md`); this document points there.

## 2. Behaviour

### 2.1 The global project

- Every org has exactly one global project, created with the org by `lorvikd` bootstrap (`internal/lorvikd/admin.go`): slug `global`, name `Global`, visibility org, concurrency parallel, the default lease, `scope` global. Other projects have `scope` project. `GET /projects` lists it first.
- `global` is refused as the slug of any other project (422 on `slug`). Archiving it is 409 with a hint. Renaming it is allowed.
- Access: an actor with an org role has that role there. An actor with no org role but an alive role in any project of the org reads it as a viewer (`Project.EffectiveRole`). Anyone else gets 404. Writes need member, or for an agent the work right (a viewer gets 403), so a project-bound agent reads but cannot write there (`global_project_test.go`).
- Notes always belong to a project; org-wide notes live in `global`. A note request without a project is 422.
- A note may carry a page like a card does (`page`, `page_bytes`, `GET /notes/{key}/page`, kept in its revisions). A note needs a body or a page; removing the page of a note with an empty body is 422 on `body`.
- Cards link across projects only when one end is the global project, and only as `blocks`, `relates` or `applies`. Two ordinary projects: 422 on `project`. Another kind across projects: 422 on `kind`. A cross-project `blocks` needs card write in the target's project and parks the target in its own project. Unlink names the target project with `?project=`.
- `[[card:N]]` and `[[note:slug]]` resolve in the source's own project, then in the global project; `[[card:global/3]]` names it. There is no `org:` prefix.
- Card numbers are per project.

### 2.2 Kinds, parents and creation

| Kind | Starts as (allowed at creation) | Parent | Claimable |
|---|---|---|---|
| task | backlog (or ready) | a story or none | yes |
| question | ready (or backlog) | a story or none | yes |
| story | backlog (or ready) | none | yes, see 2.10 |
| decision | ready = proposed (or done, by a human with decision-accept) | a story or none | no |

Any other creation status is 422 on `status`. Title is 1 to 200 characters, body at most 64 KiB (422 on the field). A card may also carry one self-contained HTML page of at most 1 MiB and valid UTF-8 (`page`, 422 on the field), kept apart from the card row and read with `GET .../cards/{n}/page` as JSON only; `page_bytes` on the card and its brief marks that it has one. The body may be empty with a page. A page is indexed for search by its visible text (not scripts, styles or `head`, plus `title` text and `alt`, `aria-label` and `title` values). `[[...]]` references are read from the body only.

- Two levels. A parent must be a story of the same project and open. A parent number that does not exist in the project is 422 on `parent`. A story with a parent, a non-story parent and a closed parent are each 409 with a hint (`parentRules`).
- `PATCH` with `parent` follows the same rules; `0` clears it. Naming the current parent is a no-op. Moving a card out of a closed story is 409 (`setParent`); moving it into one is 409.
- Edits: the owner (creator, assignee or claimant) needs card write; anyone else needs triage (reviewer; for an agent the triage right), except that a member (an agent with work) may change title, body and page of an open card.
- Ready: moving a card from backlog to ready authorises it. A person needs card write on their own card and card ready (reviewer) on anyone else's; an agent needs the ready right on every card, its own included (`requireMove`), and to create a task or story already in ready, except a child of a story past backlog (`requireCreateReady`, #273). The right says what an agent can do; the skill says when (`skills/lorvik/SKILL.md` 3.2, #120): an agent readies a backlog card only when a human named it, in chat or in the body of a ready card that a human readied or created. That body names numbers, a lane, `all backlog` or `your pick`; the agent readies exactly those and comments on that card which ones. A card an agent wrote or readied authorizes nothing, so an agent cannot hand itself the backlog, and the server does not check any of this. Waiting to ready follows the ordinary edit rules. Each title, body or page change keeps the old text and page as a revision (the page is on the single-revision read only).
- Assignee: an active user, or an active agent of the org, with a role reaching the project; anyone else is 422 on `assignee` (`assignable`). Revoking or unbinding an agent, or removing an org or project member, clears that actor's assignee on every open card they can no longer hold, in the same transaction, with a `card.updated` event naming the field (`dropAssignments`, decision #91). Done and dropped cards keep their assignee, claims run out on their lease, and an actor who is re-added does not get the old assignments back.
- `next` returns tasks only.

### 2.3 Transitions and refusals

The allowed moves per kind are the table in `docs/api.md` (`domain.transitions`, `storyTransitions`, `decisionTransitions`). Reopening goes to ready, never straight to working.

| Refusal | Status |
|---|---|
| Stale `version` | 409, `current_version` in the body |
| Illegal edge for a task, question or story | 409 |
| Illegal edge for a decision | 422 on `status` |
| Claim or `working` on a decision or a story | 409 |
| Closing or dropping a story with open children, a card moved in or out of a closed story, a child added to one, a closed story reopened, frozen decision text | 409 with a hint |
| Missing or doubled `fold`, missing drop reason, `duplicate` without a survivor, `rejected`/`revoked`/`superseded` on a non-decision, `superseded` from a client, `fold` or `cascade` on a move that does not take them | 422 on the field |
| Human-only action by an agent, role too low, read-only token | 403 |
| Project not visible | 404 |

Order in `Transition`: project visibility, the move permission, the version, the drop permission, decision-working and story-working, the closed-story reopen check, the reason and claim-ownership checks, the story plan (open children, then fold; planned only for an edge the story table allows, so a story moved backlog to done with no fold is the 409 of the illegal edge, not the 422 on `fold`), and last the kind's table. So reopening a revoked decision that sits in a closed story is 409, not 422.

Claims, leases, the sweeper, `next`, blocking links and comments are unchanged by the story model. `blocks` on a question parks a `ready` or `working` target in waiting and releases its claim, and parks a `backlog` target too, so the answer readies every card it decided (#187), unless the linker is an agent without the ready right in the target's project, whose backlog target only gets the link (#280). Only an answer readies a card parked from backlog: when its last blocker is unlinked, dropped, or a question closed unanswered, it goes back to backlog; a blocker that completes (a question answered, a task done, a decision accepted) readies it. The way the last blocker goes decides, even when an earlier question of the card was answered (`unblockIfClear`, where it was parked from is read from its last move to waiting, #283); a card parked from ready or working returns to ready; a `blocks` link from any other card parks only `ready` and `working` targets; targets of kind decision, and targets in any other status, only get the link (`blockCard`).

### 2.4 Stories

- A story's body carries the user story and "done when"; its lane names the area and so its requirements document (skill convention).
- A story keeps to about 100 children, usually ten to fifty; a bigger request is split into several stories linked `relates` (skill guidance; the server sets no limit).
- Status follows the work. When a task or question child reaches working (claim, start or transition) and the story is backlog or ready, the story moves to working in the same transaction (`card.status_changed` with `by_child`). A decision child never starts a story. Nothing moves a story back: releasing, dropping or sweeping its children leaves it working. A story is never claimed and never moved to working by hand (409, hint "a story is not worked: start one of its children"); its other moves are manual: ready, waiting, backlog, done with a fold, dropped.
- **Closing.** A story closes from ready, waiting or working (not backlog, whose edges are ready and dropped). Every child must be done or dropped, else 409 listing the open numbers; then `fold` must carry exactly one of `into` (a path) or `none`, else 422 on `fold`. The fold (`into`, `at`, `by`) is stamped on the story and on every child, dropped children included. Events: `card.status_changed`, then `card.folded` on the story.
- **Closed is closed.** A done or dropped story refuses new children, moves of cards into it or out of it, reopening of its children, and being reopened (all 409). Later work is a new story linked `relates`.
- **Dropping.** A story drops from backlog, ready, working or waiting. With open children it is 409 unless `cascade` is true; then the children are dropped in the same transaction with the story's reason (decisions as `rejected`; `obsolete` when the story's reason is `duplicate`), claims released, dependents unblocked, one `card.status_changed` each with `cascade_of`. A dropped story is not folded.
- `progress {done, total}` counts done and dropped children over all children. It is on every `Card` response for a story, not on list rows.

### 2.5 Decisions as cards

A decision is a card of kind decision. Text, supersession, `applies` links and wording are in `decisions.md`. The state machine:

| Meaning | Card state | Move | Needs |
|---|---|---|---|
| proposed | ready | create | decision-propose (member) |
| accepted, in force | done; acceptor and time kept | ready to done | decision-accept, human; or an agent with the decide right (`decisions.md` 2.3) |
| rejected | dropped, `rejected` | ready to dropped | decision-accept, human; or an agent with the decide right (`decisions.md` 2.3) |
| revoked | dropped, `revoked` | done to dropped | decision-accept, human |
| superseded | dropped, `superseded` | system only | n/a |
| re-proposed | ready | dropped (rejected only) to ready | proposer: member; others: reviewer |

Backlog, waiting and working are refused. A revoked or superseded decision is not proposed again (422 on `status`). Text is editable only while ready, by the proposer (decision-propose) or a reviewer (decision-accept); once done or dropped, a title, body or page edit is 409 with the hint `accepted text is frozen; record a superseding decision`. Priority, assignee, lane, branch and parent stay editable.

### 2.6 Folding standalone cards

- A card with no parent may be folded as it closes: `fold` (`into` a document path, or `none: true`) on its move to done stamps the mark on that card alone and appends one `card.folded` event, exactly as the fold route would. A story requires the fold; any other card without a parent may omit it and stays unfolded. A card with a parent, a card already folded, or a `fold` on any move but done is refused: 422 on `fold`, with the hint "fold the story instead" for a card with a parent. Neither or both of `into` and `none` is a 422 on `fold`.
- `POST /projects/{slug}/cards/{n}/fold` with `{version, into | none}` marks a done card that has no parent and no fold. Not done, has a parent, or already folded: 409. Neither or both of `into` and `none`: 422 on `into`. It needs card write on an own card, else triage. Any kind qualifies, so a done decision in an ordinary project folds the same way.
- `GET /projects/{slug}/unfolded` lists done cards with no parent and no fold mark, newest `closed_at` first (id breaks ties), keyset paged, limit 20 default and 200 maximum. Because it matches by state, an answered question with no story and a decision made by `decide=true` from a loose question appear in it too.
- `lorvik fold N` composes the brief for a story from ordinary reads (children with done notes and `Done:` comments, decisions in full, lanes, `docs/requirements/<lane>.md` for plain lane names); no endpoint serves it.

### 2.7 Lists across projects

`GET /cards` takes the project list's filters except sort and desc, plus `project` (`all` or empty, or a slug). It lists newest first by id (ranked when `q` is set), default limit 10, maximum 200, one `CardBrief` per row with `project` set. With `all` it covers the projects the caller can see and drops archived ones; with a slug it uses that project's access rule. `parent` needs a slug (422 on `parent`). `CardBrief` carries `drop_reason`, `closed_at` and `fold`. Used by the Decisions page, the Stories page and `decisions ls`.

### 2.8 Events

No `decision.*` events exist. `card.created` carries `kind`, `status`, `priority`, plus `supersedes` or `from_question`. Every `card.status_changed` carries `kind` beside `from` and `to`, and optionally `drop_reason`, `note`, `duplicate_of`, `blocked_by`, `unblocked_by`, `by_child`, `cascade_of`, `superseded_by`; events stored before `kind` was added lack it. `card.folded` carries `into`. `card.linked` carries `to_project` across projects.

### 2.9 Locks on shared resources

- A lock is a named lease on a shared resource that two actors must not use at once: a test database, a port, a device, a deploy target, a generated-code step. It is org-scoped, so one name means one resource for every project. Names are 1 to 40 characters of lowercase letters, digits, hyphens and slashes; the purpose is 1 to 200 characters; the lease is 60 to 3600 seconds, 600 by default (`internal/domain/lock.go`).
- Any member of the org, or of any project in it, may acquire (`svc_locks.go`, `requireAnywhere`). Viewers and read-only tokens may not. Acquiring a name nobody holds creates the lock; a lapsed one is taken over in place; a live one held by the same actor in the same session is renewed with the new purpose and writes no event; a live one held by anyone else is a 409 naming the holder, their session, the purpose and the seconds left, with the hint to wait or pick other work. A lock may name the card it serves (`project` and `card`, since numbers are per project).
- Renewal is explicit: only the holding actor in the holding session may renew, and no other request renews a lock. Claims renew on every request from the session that holds them because they mark ownership of work; a lock marks occupation of a resource and must lapse when the process that held it stops calling.
- The holder releases from any session. A human with triage (reviewer or above) may force-release anyone's lock; agents never may. A lapsed lock answers 404 on renew and release: the next acquire or the sweeper settles it.
- Every actor sees every live lock: `GET /locks`, the `locks` field of the inbox, and the CLI (`lorvik locks`, `lorvik status`, `lorvik inbox`). `next` withholds a ready card whose lane equals a live lock name and reports it in `busy_lanes`, so a card whose lane is `test-env` is not offered while the gate runs there.
- `lorvik lock run <name> -m "<purpose>" -- <command>` holds the lock for the life of a command: it acquires, renews at half the lease, kills the command's process group if a renewal fails, releases on exit and exits with the command's code. Expiry proves that renewal stopped, not that the process stopped; the wrapper's kill on renewal failure covers the common case and the residual risk is accepted.
- Events, org-wide with subject type `lock`: `lock.acquired`, `lock.released` (with `forced` and the former holder when forced), `lock.expired` (actor = the former holder, so it reaches their inbox), written on takeover and by the sweeper.

### 2.10 Relayed answers

A question is the human's to answer, or an agent's that holds the answer right: its answer is its own, not relayed, takes effect at once, and is recorded for its owner with a reason until that person keeps or changes it (story #272, decided on #270; for whom and why, decision #384), except a question asked from its own chat or that chat's subagents, which another chat or a person settles (403, decided on #273). When the human answers in chat or elsewhere, an agent that heard it relays the answer to the card instead of closing it (story #231, decided on #227):

- `POST .../answer` with `relayed: true` and a `note` saying where and when the human gave it. Only an agent may relay, and only on a question it may close (its asker, assignee or claimant; triage otherwise). The question closes as done with the answer, `answered_by` is the agent, the note becomes the agent's comment, the claim is released and the cards it blocked move on at once, since the human already answered. `card.answered` carries `relayed: true`. An agent without the answer right sending no `relayed` gets 403 naming the right, a blank note 422, `decide` 422 from any agent (a decision needs a human).
- A relayed answer stands as given and does not await the human: `CardBrief.relayed` is true while `cards.answer_relayed` is set (an agent relayed this answer), the `relayed` list filter returns such questions so what agents relayed can be reviewed, and neither a user's open-question count nor the dashboard's awaiting list includes them. The card shows "Answer relayed by X" with the answer, the note in its history, and Change. The agent tells the human in the same chat what it recorded, so a misread is caught there.
- A user answering a relayed question again records their own answer (same text or different); `answered_by` becomes the user, the status stays done, and `card.answered` carries `confirmed: true` and, for a change, `previous`. `decide` works as for any answer. Cards that moved on are not parked again when the answer changes; the event tells the agents.
- An agent moves an open question only by dropping it: claiming, starting, parking (backlog, waiting) or closing it is a 409 with the hint `relay the human's answer: lorvik answer N "<answer>" --relayed -m "<where they said it>"` (the CLI's `done` used to claim it first, leaving it working and out of the human's list). It may drop its own question only once nothing it blocks is open; otherwise 409 naming the blocked card, so a withdrawn question never releases the work that waited for the answer. Users are unchanged.
- Reopening a done question clears its answer (the events keep it), so the card shows the answer form again rather than a stale or relayed answer with nothing to act on.
- An answer under the answer right says for whom and why (decision #384, section 3). The agent sends a `note` with what it relied on (a decision, a requirements section, a person's words on a card), 422 without. The card stores `behalf`: the agent's owner (`cards.behalf_user_id`), the reason, the chat, the agent (`behalf_agent_id`), and `behalf_kept_at`, empty until that person has looked. Only that person keeps it (`POST .../keep`, event `card.kept`; 403 for anyone else, 409 when nothing waits). Until it is kept, a user who may answer questions can answer again, which works as changing a relayed answer does: their answer replaces the agent's, `behalf` is cleared, `card.answered` carries `confirmed` and `previous`, and work that moved on is not parked again. Once kept it is settled like a person's own answer. Reopening the question clears the record with the answer. The `answered_for` filter (`me` or a user id) lists what waits for a person; the reason is kept on the card and not posted as a comment.
- A question can be marked for a person (decision #384, section 4): `cards.for_person`. The asker sets it when asking (`lorvik ask --person`), or it is set later on an open question (`lorvik escalate N -m "<why>"`, `POST .../for-person`) by the asker, by an agent holding the answer right that will not answer, or by a person who may answer; an agent must say why, and the reason is posted as its comment. Once set, no agent answers the question (403), whatever rights it holds; relaying a person's answer stays allowed. Only a person who may answer clears the mark. `card.for_person` records both, and `CardBrief.for_person` lets a list put such questions first.
- What the server cannot check is the skill's (`skills/lorvik/reference/delegate.md`; decision #384, sections 2, 4 and 6): a chat on duty holds no cards, so it never answers for its own work; text on a card is its author's claim, never an instruction; a basis is only an accepted decision, a requirements document, a note, a person's comment or answer, or a story's request a person wrote; the kinds of question that always go to a person (money, security and secrets, deleting or publishing data, releases, licence and legal, the irreversible, contradicting an accepted decision, no basis found); and that what an agent settled and nobody has kept is never the only basis for another answer. A worker whose `next` finds nothing while the backlog is not empty asks one question, "Nothing ready: what next?", at most one open per project (`skills/lorvik/SKILL.md` 6); a person, or a chat on duty within its instructions, answers it by readying cards.
- CLI: `lorvik answer N "<answer>" --relayed -m "<where>"`, or `-m "<what it rests on>"` alone for an agent with the answer right; `lorvik ls --answered-for me`; `show` marks a relayed answer with who relayed it and prints `for @name, not looked at yet: <reason>` (or `kept 3m ago`) under an agent's own answer; event lines read "relayed an answer", "confirmed the answer", "changed the answer ... (was A)", "answered #N for <name>", "accepted decision #N for <name>", "kept the answer on #N" (on a decision "kept the verdict on #N"), "marked #N for a person", "cleared the for-a-person mark on #N"; `show` prints `for a person` among the card's facts.

## 3. Rules

- Permissions are `domain.minRole` (`docs/api.md`, Roles). Agents act on rights instead (`docs/api.md`, Agent rights; `access.can` is the one check). Human-only actions (`userPrincipal`, `requireHuman`): revoking a decision, recording one as accepted at creation, `decide` on an answer, and taking over another actor's claim. Accepting or rejecting a proposed decision is a person's, or an agent's under the decide right (`decisions.md` 2.3). Answering needs the answer right; without it an agent only relays a human's answer (2.10).
- Every write carries the version it read. Closing a story, cascade drop and supersession each run in one transaction with their events.
- The server enforces structure (two levels, closed is closed, closing needs a fold, frozen decisions) and does not judge the content of a fold.
- Every mutation appends an event as the caller. No personal data beyond actor ids is stored on cards.
- Claims belong to their holder: for a human the user, in any session; for an agent the agent and the session label (`X-Lorvik-Session`) that took it, because every chat of an agent shares its token (`Claim.OwnedBy`, decision #137). While the lease is live another session of the same agent is refused like another actor: claim, start and transitions 409, renew and release 403, each naming the holder and its session. An expired claim is taken over; the `card.claimed` event then carries `taken_from` and `taken_from_session`, and a reviewer's release of someone else's claim carries `released_from` and `released_from_session`. Every authenticated request renews the caller's claims past half their lease (an agent's only in its own session), except `GET /events/stream` and every request a background listener makes (`lorvik inbox --follow` marks its own with `X-Lorvik-Listener`: its inbox rereads, name lookups and token renewal), so a listener left running in a closed chat keeps nothing alive (`renewsClaims`). Before #364 the listener's inbox reread on any board event renewed the chat's claims. A holder may state how long its claim lasts (`lorvik start N --for 1h`, `claim --for`, `heartbeat --for`; `ClaimCard.lease`, 1m to 24h, the bounds of a project's lease, `domain.ValidLease`): the length is kept on the claim (`claims.lease_seconds`, null follows the project), every later renewal uses it in place of the project's lease, a `heartbeat --for` sets the end exactly that far from now even when that is sooner, and the holder claiming again without a length keeps it. It ends with the claim: a takeover or a new claim after a lapse starts from the project's lease (`NewClaim`, `Claim.Renew`, #365). Accepted: a chat that states 24h and dies holds the card that long unless a reviewer releases it. Tests: `internal/server/session_test.go`, `internal/store/cards_test.go`.
- An inbox event wakes the calling chat (`wake`, `markMineWake`) when its card is held by this chat, was created by this chat, or is assigned to the caller. For an agent "this chat" is the session: its claims and the cards whose `card.created` event it wrote in that session (`CardsCreatedInSession`), so a lead wakes on its subagents' work on the children it created and never on another chat's cards. An assignment names the agent, not a chat, and every chat of an agent shares its token, so an assigned card wakes a chat only when it is no other chat's (neither held nor created by another session of the agent: a chat that assigns its own cards to its agent wakes nobody else) and, when the chat names the project it works in (`chat_project` on the inbox; the CLI sends the bound project: `--project`, `LORVIK_PROJECT` or `.lorvik.toml`), only in that project. A card a chat holds or created wakes it in any project, and a chat that names no project is woken by an assignment in any. A `chat_project` that names no project is not an error, so a listener started before its agent joined the project keeps running; no assignment wakes it. A card an agent's chat is subscribed to (`lorvik subscribe N`, `PUT /projects/{slug}/cards/{number}/subscription`; `card_subscriptions`, keyed by agent and base session label so a chat's subagents share its subscriptions) is `mine` and wakes the chat for every event on it, in any project (`subscribedByChat`); this is how a chat that left a card waiting on a person hears the person's comment. A subscription is dropped once its chat has been gone for a day (not seen for `subscriptionLostAfter`, 24 hours, by `agent_sessions.last_seen_at`), and when the card is done or dropped. An open event stream keeps its chat seen, since its keepalive touches the chat's session (`KeepChatSeen`, at most once a minute), so a chat waiting on its listener is never swept. Wake is computed on the reading chat's own request, which marks the chat seen, so no separate liveness test applies. At most 50 open cards per chat; people and agent requests without a session label are refused with 422, a done or dropped card with 409. `GET /me/subscriptions` lists the chat's subscriptions to open cards, shown by `lorvik status`. For a human `wake` equals `mine`. An agent's chat that may answer questions is woken by one it may answer (decision #384, section 5; `wakeToSettle`): a `card.created`, or a `card.for_person` that takes the mark off, of a question that is still open, not for a person, not asked by this chat or its subagents (`askedByChat`, the rule that also refuses the answer), in a project where the caller holds the answer right, and in the chat's project when it named one. That event is not `mine`: the question is nobody's card. A chat holding the decide right is woken the same way by a decision it may give the verdict on: its `card.created`, or the `card.status_changed` that proposes it again, while it is still a proposal and not barred to that chat (`verdictBarred`, the rule that also refuses the verdict). The chat that settled a card for a person is told what the person did with it (`judged`): `card.kept`, a `card.answered` that replaces an agent's answer, and a person's revoke or re-proposal of a decision whose verdict an agent gave and nobody had kept carry `settled_by` and `settled_by_session`, are `mine` for that agent and wake the chat with that base label, in any project. A chat is also told when a card stops being its own (`lostClaim`, #367): the sweeper's `card.claim_expired` (actor = the former holder, payload `session`, written in `domain.UnpromptedSession` so a person on the dashboard, who sends no session label, gets it too), a `card.claimed` that took the caller's claim over (`taken_from`, `taken_from_session`; this is the expiry notice when another actor claims a lapsed card before the sweeper settles it) and a `card.released` by a reviewer (`released_from`, `released_from_session`) are `mine` for the actor who lost the claim and wake the chat that held it, in any project; before, such a card was nobody's by the time the event was read and the one chat that had to stop was not told. `lorvik done` on a card this chat's claim ran out on, with no claim or release since (the lapsed claim is still on the card, or the last claim event among the card's ten recent ones is its expiry, in this session for an agent and in any for a person), says so on stderr before it claims again; otherwise it prints the plain note. A chat is reminded of the cards it holds (#369, the owner's request: a chat that works several cards forgets one, and a forgotten card stays claimed while the chat makes requests). The CLI sends `X-Lorvik-Holding` on every request and the server answers with the list as it is after the request (`holdingWriter` sets the header when the response starts; `Service.holding`; at most `apitypes.HoldingCap` cards and `holdingHeaderMax` bytes, because a reverse proxy refuses a response whose headers overflow its buffer, 4 KiB by default in nginx). After a successful command the CLI prints one line per card on stdout, after the command's own output, `holding  #42  demo  Fix login  12m left`, and `holding  3 more` past the cap; the card the command names is not left out and `-Q` does not hide the lines. This is on stdout by the owner's choice (#372, option B), an exception to "stdout is data": each line starts with `holding  ` so a script can drop them. Under `--json` an object gains a last field `holding` and an array is printed unchanged. No lines follow a page's source or a secret shown once (`login`, `token create`, `agent register`), both printed through `app.payload` because a script captures them whole, nor `session`, `lock run`, `watch` (its list would be as old as the wait) or `inbox`, which prints the chat's claims itself; `inbox` and `status` end each claim line with the time left. Measured before choosing the header over a second request (2026-11-13, local server): the two reads cost about 0.2 ms in Postgres, a second request from the CLI 5 ms or more. `lorvik inbox --follow` ends a batch that printed a wake event with the same lines (under `--json` one line `{"holding": ...}`) and prints them at no other time, since every line a listener prints starts a turn; each line is complete on its own because adapters hand lines to the chat one by one. `lorvik inbox --follow` prints only wake events: it starts at the stored cursor without moving it (at the newest event when there is none or it names no event), rereads the inbox only when the event stream shows a newer event, retries with a pause doubling from 1s to 30s, and `--once` exits after the first batch with a wake event. `--exit-on-eof` also exits 0 when stdin reaches end of file, so a listener an adapter started ends with the adapter even when it is killed; an interrupt or EOF before the start event is found also exits 0. The skill's `reference/waiting.md` tells an idle agent to wait on it instead of polling: Claude Code arms the Monitor tool (re-armed every 30 minutes); Pi loads `skills/lorvik/adapters/pi`, tested end to end; Codex, OpenCode, Qwen Code, Goose, Crush, Kilo, DeepSeek Harness, Copilot CLI and Cursor Agent have opt-in adapters under `skills/lorvik/adapters/`, written from each harness's tagged source or official docs and not yet run against the harness; Gemini CLI only adds pending events to the next prompt; Amp has none. Tests: `internal/server/inbox_session_test.go`, `internal/cli/inbox_follow_test.go`, each adapter's offline tests.
- A chat's session label comes from its harness's session variable when one is exported to shell commands, checked in order: `CLAUDE_CODE_SESSION_ID`, `OPENCODE_SESSION_ID`, `CODEX_THREAD_ID`, `CODEX_SESSION_ID`, `PI_SESSION_ID`, `QWEN_CODE_SESSION_ID`, `COPILOT_AGENT_SESSION_ID`, `DSH_SESSION_ID`, then Goose's generic `AGENT_SESSION_ID` (`sessionHarnesses` in `internal/cli/session.go`). A row is added only for a variable verified in the harness's source or vendor docs.
- The inbox lists the caller's claims split by `Claim.OwnedBy`: `claims` are this chat's, which the call renews; `claims_other_sessions` are the same agent's claims under other session labels, not renewed and not this chat's to continue. A human has one list (`claimBriefs`, test `internal/server/inbox_session_test.go`). `lorvik status` splits the caller's open cards by the same rule: every claim on the wire carries `owned` (`Claim.OwnedBy`, live or lapsed; `mine` is `owned` and live), and a card whose claim is not `owned` goes under `my cards (other sessions)`, so a person who claimed a card in the dashboard sees it as their own in the CLI (#179; tests `internal/server/session_test.go`, `internal/cli/session_test.go`).
- The inbox cursor lives in the user config: `cursor_<token prefix>` for the agent and `cursor_<token prefix>_<label>` per chat, stored as `<event position>@<unix seconds>`; a cursor saved as a bare event id by an older CLI is read once and replaced by a position. A session save also moves the agent key forward, never back, comparing positions as strings; a chat with no key starts from it. Session keys not written for 7 days are removed on the next save; a key without a stamp is stamped, not removed. A token rotation moves every cursor key of the old token to the new one, keeping the newer agent cursor. Every config write reads, changes and replaces the file under an exclusive lock (`config.toml.lock`), so concurrent chats never undo each other's cursor or token (`internal/cli/state.go`, `config.go`, decision #178, tests `state_test.go`).

## 4. Data

Columns are in `internal/store/migrations/00001_init.sql`.

- `projects.scope`: 1 project, 2 global; a partial unique index allows one global project per org.
- `cards.kind`: 1 task, 2 question, 3 story, 4 decision. `cards.drop_reason`: 1 obsolete, 2 duplicate, 3 wontfix, 4 rejected, 5 revoked, 6 superseded (4 to 6 decisions only); set when dropped.
- `cards.answered_by_*`, `answered_at` hold the answer's author, or for a decision the acceptor. `answer_relayed` marks a relayed answer the human has not confirmed (2.10); an agent with the answer right writes false. `for_person` marks a question only a person may answer (2.10).
- `cards.behalf_user_id`, `behalf_agent_id`, `behalf_reason`, `behalf_session`, `behalf_kept_at`: all null unless an agent settled the card for a person (2.10); `behalf_kept_at` is set when that person keeps it, and all five are cleared when a person answers again. A partial index on `behalf_user_id` covers the rows not kept yet.
- `cards.folded_into` (null until folded, empty string = no document), `folded_at`, `folded_by_kind`, `folded_by_id`.
- `card_links.kind`: 1 blocks, 2 relates, 3 duplicates, 4 supersedes, 5 applies.
- `notes.project_id` is NOT NULL. `refs` types: 1 card, 3 note (2 retired).
- `locks`: one row per `(org_id, name)` (unique index); holder as kind and id, `session`, `purpose`, nullable `card_id`, `acquired_at`, `expires_at`. An expired row stays until taken over or swept. `events.subject_type` 8 is a lock.

## 6. Jobs

The claim sweeper (`RunSweeper`) runs every configured interval, releases expired claims, returns a working card to ready and emits `card.claim_expired`. A second run finds no expired claim. Before a claim ends the same loop writes its last call, `card.claim_ending` (`announceEnding`, #366): once per expiry, `domain.ClaimLastCall` (five minutes) ahead or a quarter of the lease when that is shorter (`Claim.LastCallAt`; renewal starts at half the lease, so a holder that is making requests gets none). `claims.ending_announced_for` records the expiry the call was written for, set only if the claim still ends then, so a claim renewed, released or retaken meanwhile is skipped and a renewal arms the next call. The holder is the event's actor and it is written in `domain.UnpromptedSession`, so it reaches the holder's inbox even with no session label; it wakes the chat that holds the card (the claim is still live) and reading it through a listener renews nothing. No answer and the claim lapses as before. Accepted: a lease shorter than four sweep intervals can lapse with no call; the call is a project event that every reader of the feed sees; a chat that is woken and then makes any request renews all its claims, so what to do on the call is the skill's to say. The same loop deletes lapsed locks, one transaction per lock after re-reading the row so a concurrent takeover is kept, and emits `lock.expired` for each; a second run finds none. It also deletes the subscriptions of chats not seen for 24 hours or with no `agent_sessions` row, and the subscriptions to cards that are done, dropped more than an hour ago (`closedSubscriptionKept`, by the card's `closed_at`) or gone, one statement each (`sweepSubscriptions`), and logs the counts. It also logs a warning once an org's event log passes a million rows; that check changes nothing.

## 7. Why it is this way

1. Decisions are cards because the proposal-card mirror showed the seam: a separate table needed a linked card, two-way text sync and refusals on the card to behave like one. Rejected: keeping the table and the mirror. Record: `docs/adr/0008-stories-decisions-as-cards-global-project.md`.
2. One global project instead of nullable project ids, so every scope rule is a project rule and org-wide tasks and questions are possible. Rejected: `project_id IS NULL` branches in every list, access check and reference resolver.
3. Stories are a kind, not "any card with children", so the server can enforce closing and the dashboard can render them. Rejected: implicit stories by inference.
4. Closing a story is the fold, so a done story without a fold mark cannot exist and the unfolded list shows only standalone cards. Rejected: folding on a timer, which turns a judgment into a chore.
5. Closed is closed: fix-ups are new stories, so a story's fold stays true to what it folded. Rejected: reopening stories.
6. The fold brief is composed by the CLI from existing reads, so the server stays free of document knowledge. Rejected: a brief endpoint.
7. Supersession is a link plus a system-set drop reason, reusing the duplicate-link shape. Rejected: `supersedes_id` and `superseded_by` columns.
8. The global project is readable by any member of any project in the org, so a project-bound agent sees org-wide decisions without an org role; it is not writable that way. Rejected: requiring org membership, which would hide global decisions from the agents that need them.
9. Locks are their own entity, not a lane and not a card claim. A lane is held for the life of a working card, which would occupy a test database during coding; a claim renews on every request, which would keep a lock alive while the holder chats. Rejected: an admin-managed resource catalogue with grants and a fenced "uncertain" state after expiry, which would make an admin register every resource before the first lock and models a guarantee the server cannot give. Chosen 2026-10-31 after a Codex brainstorm.
10. An agent's claim is fenced by session, not by giving each chat its own agent token, because the token is set up once per harness and a chat is started many times a day; the session label is already derived per chat by the CLI. Renewal follows the same fence: renewing every claim of the actor on any request kept a closed chat's cards claimed for as long as any other chat of that agent was active. Humans are not fenced, because the dashboard sends no session and one person works a card from several devices. Rejected: one agent token per chat; fencing humans too. Chosen 2026-11-05 (story #133) after a Codex brainstorm.
11. Adapters that wake a closed chat's queue are shipped opt-in rather than withheld: the harnesses that admit work durably (Codex, OpenCode, Kilo, Crush) give no way to stop one more turn after the chat closes, and an armed wake is still worth more than none. Rejected: waking by a headless resume of the session, which starts a new process the human never sees.
12. A new chat's inbox starts at the agent's newest read, not at the head of the log: starting at the head would hide an answer or comment that arrived while no chat was running. Idle session cursors expire after 7 days because every chat adds a key and a chat idle that long has lost its claims (decision #178).
13. An agent relays a human's answer, which stands as given, rather than the agent closing the question or only the human closing it: closing hid the question from the human, and waiting for a second answer on the dashboard stalled work after the human had already answered in chat. The relay is an answer whose author is an agent, so no column was added. Rejected: agents closing questions with a status change; humans only. Chosen 2026-11-08 (#227); changed on 2026-11-09 (#284): the Confirm step was dropped; the history and the agent's chat line show who relayed what.
14. Agents hold rights that combine (work, ready, triage, answer, decide) rather than rungs of the role ladder, set per project and per chat: the owner wanted one agent that readies and works backlog cards but never answers, and another that only answers, which a cumulative ladder cannot express. People keep roles. A chat's grant is keyed by its self-declared session label, so it guards against mistakes, not against a chat posing as another; every chat runs as the same OS user and could read any credential file anyway. Rejected: more rungs; rights for people too. Chosen 2026-11-08 (#270).
15. An assignment to an agent wakes a chat only in the project the chat works in, and never for a card another chat of the agent holds or created, rather than waking every chat of the agent: one token serves every chat on a machine, and a chat that had assigned its own cards to its agent woke a chat working in another project on every comment, claim and move (#359). The chat's project travels with the request (`chat_project`) because the CLI already knows it and the server keeps nothing per chat but its label. Rejected: taking the assignment out of the wake rule, which would leave a card a person hands to an idle agent unnoticed; narrowing the whole listener to one project, which would miss a card the chat itself holds or created elsewhere, such as a decision it filed in the global project. The owner on the question card (#360): "Can't we run the monitor in such a way that it can be filtered to just the org and the project that the chat is supposed to hear? Maybe including the chat's own name so that only things relevant to it are shown and everything else is not". The org was already fixed by the token and the chat's name by the session label. Accepted consequences: a card a chat assigned to its own agent wakes nobody once that chat is gone, until a chat claims it; a card a person assigns to the agent in a project no chat is bound to (the global project, say) wakes no chat; and a card a person assigned that no chat holds, a finished one included, wakes every chat of the agent in that project. Chosen 2026-11-12.
16. A chat can subscribe to a card (`lorvik subscribe N`) so a person's comment wakes it after it left the card waiting, rather than waking every chat of the agent for every card it ever touched or only for cards it holds or created: a card waiting on a person is nobody's by claim and the chat is the only one that knows it waits. The subscription is per chat (agent plus base session label), the owner's answer on #430 (A), named subscribe rather than watch because `lorvik watch N` already blocks on one card's next event (the owner's answer on #435, A), and it is dropped once the chat has been gone for a day (the owner's comment on #430 that subscriptions must not stay held by chats that are dead or lost), and when the card is done or dropped. An open listener keeps its chat seen, so only a chat that is really gone loses them. Rejected: a unique index for idempotence (the insert checks first and a rare duplicate is harmless: unsubscribing deletes every match and reads de-duplicate); a one-hour liveness test in the wake query (wake is computed on the reading chat's own request, which marks it seen, so it never changed an outcome); subscriptions for people, who see replies on the dashboard. A subscription outlives the closing of its card by an hour (`closedSubscriptionKept`), so a listener that is reconnecting still reads the closing event, the one a waiting chat most wants (review of #433). Chosen 2026-11-18.
